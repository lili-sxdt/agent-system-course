# 第2章 依赖注入（DI）与容器

> 上一章讲了"要拆成插件"。但拆完的插件，**谁来管、谁来把它们串起来**？答案是**容器**。这一章讲清楚：依赖注入（DI）是什么、容器在干嘛。

---

## 2.1 DI 解决什么问题 {#sec-1}

**大白话**：假设 A 要用 B。最直觉的做法是 **A 自己 `new B()`**。但这样 A 就被"焊死"在 B 上了——想换成 B' 就得改 A。

**换成 DI**：A **不自己造 B，而是"告诉容器：我需要一个 B"**，容器负责把 B 塞给 A。A 只管用，不管从哪来。

**专业**：**依赖注入（Dependency Injection, DI）**是一种"把依赖从外部传入、而非内部创建"的设计。它让组件**依赖接口而非实现**，从而实现解耦、可替换、可测试。背后思想叫**控制反转（IoC）**——控制权从组件内部反转给了容器。

```ts
// 写死：A 焊死在 B 上
class A { private b = new B() }

// DI：A 只说"我要一个 B"，由容器给
class A { constructor(private b: B) {} }
```

---

## 2.2 cordis / context 的角色 {#sec-2}

**大白话**：DSH 用 **Cordis** 当那个"容器"，核心对象叫 **context（ctx）**。你把插件放进 ctx，插件之间就通过 ctx 互相找、互相用。

**专业**：Cordis 是一个**插件容器 / IoC 框架**。`ctx` 是贯穿全系统的上下文对象，提供注册、依赖、事件、生命周期能力。所有 `dsh-*` 包都是"注册进 ctx 的插件"——这就是 DSH 的组织方式。

```ts
const app = new Context()
app.plugin(myPlugin)      // 把插件装进容器
```

---

## 2.3 容器里有什么 {#sec-3}

一个容器大致管三样：

| 东西 | 大白话 | 作用 |
|---|---|---|
| **注册表** | 花名册 | 记着"系统里有哪些插件/服务" |
| **服务** | 公共设施 | 插件对外提供的能力，别人能取用 |
| **生命周期** | 开关机流程 | 控制插件何时加载、初始化、卸载 |

**一句话**：**容器 = 一个"管家"，负责登记、分发、开关。** 插件只管干活，不用自己操心"我在系统里怎么被管"。
