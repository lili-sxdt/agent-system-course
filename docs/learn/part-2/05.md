# 第5章 配置系统

> 最后一章。插件要能"按需定制"，就得有**配置系统**。这一章讲：配置项怎么定义、优先级怎么排、怎么校验和写回。

---

## 5.1 一个插件的配置项怎么定义 {#sec-1}

**大白话**：给插件一张"设置表"——哪些能调、默认是什么、什么类型。用户只改他关心的那几项。

**专业**：用 **schema（模式）** 声明配置：字段名、类型、默认值、校验规则。容器加载插件时，把用户配置和默认值合并后传给插件。

```ts
export interface MyPluginConfig {
  /** 状态栏是否开启 */
  enabled: boolean
  /** 轮询周期（毫秒） */
  pollMs: number
}

const defaultConfig: MyPluginConfig = {
  enabled: true,
  pollMs: 5000,
}
```

**好处**：类型安全 + 有默认值 + 可校验。**别让插件在运行时才发现"配置缺了"。**

---

## 5.2 优先级：默认 < 用户 < 预设 {#sec-2}

**大白话**：配置可能有多个来源，谁说了算？按这个顺序（后面的覆盖前面的）：

```
默认值  <  用户配置  <  预设/命令行
```

**专业**：配置**合并**遵循优先级：底层是默认值，用户配置覆盖它，特定场景（预设、命令行参数）再覆盖。这样既有合理默认，又能精细控制。

```ts
const finalConfig = { ...defaultConfig, ...userConfig, ...presetConfig }
```

**要点**：**越"临时/具体"的，优先级越高。** 用户改的是"这个项目"的配置，预设是"这次运行"的覆盖。

---

## 5.3 写回与校验 {#sec-3}

**大白话**：用户改了设置，要**存下来**（写回配置文件），下次还在；改错了要**拦住**（校验），别让它带着坏配置启动。

**专业**：
- **校验**：写回前用 schema 检查类型/范围，非法就报错并保留原值。
- **写回**：序列化到配置文件（如 JSON），注意**原子写**（先写临时文件再替换，避免写一半崩了损坏配置）。
- **换行符**：写回时注意结尾换行，避免"内容没变却显示已修改"的假 diff（真实项目里踩过）。

```ts
function writeConfig(path: string, cfg: MyPluginConfig) {
  // 示意：真实项目应做原子写 + 校验
  fs.writeFileSync(path, JSON.stringify(cfg, null, 2) + '\n')
}
```

## 验收清单 {#sec-4}

- [ ] 能说出配置项**该声明什么**（类型 / 默认值 / 校验）。
- [ ] 能排出配置**优先级**（默认 < 用户 < 预设）。
- [ ] 能说出**写回要注意的两点**（校验、原子写）。
- [ ] 知道"配置写回"为什么要小心换行符/格式。

**追问**（答不上来就回看 5.3）：用户把 `pollMs` 填成了 `"abc"`（字符串），你的插件应该在**什么时候**发现这个问题——启动前校验，还是运行到一半崩？为什么？
