# 第1章 为什么要插件化

> 从这一部分开始，我们给 mini-harness"上骨架"。第一件事：**把功能拆成一个个可插拔的单元**。这是 DSH 能塞下几百个模块还不乱的根本原因。

第一部分第5章你写出的裸 Agent，所有东西挤在一个文件里。它能跑，但**改一处、动全身**。这一章我们讲怎么拆。

---

## 1.1 把功能拆成可插拔单元

### 1.1.1 一个功能 = 一个插件

**大白话**：别把"读文件、算数、查网页、记日志"全塞进一个程序。**一个功能做成一个"插件"**——独立的小盒子，有自己的开关。

**专业**：**插件（Plugin）**是一个自包含的功能单元，遵循统一的接口被系统加载。系统不需要知道插件内部怎么写，只要它符合"怎么装、怎么卸、对外提供什么"的约定。

### 1.1.2 插件如何"装 / 卸"

**大白话**：装 = 把它加进系统、让它开始工作；卸 = 从系统里拿掉、让它停止、清干净。**能装能卸**，才叫插件。

```ts
// 示意：一个插件就是一个可被系统加载的单元
export function myPlugin(ctx: Context) {
  ctx.on('ready', () => console.log('插件已加载'))
}
```

---

## 1.2 插件的优点

### 1.2.1 复用

写一次"读文件插件"，哪个项目都能装。**不重复造轮子。**

### 1.2.2 开关与控制

想要就装、不想要就卸。**出问题的插件能一键关掉**，不影响其它功能——这是"可运维"的关键。

### 1.2.3 独立演进

插件之间**互不干扰**：改 A 插件不会把 B 插件改坏。团队可以并行开发（还记得我们聊过的"怎么安排人"吗？靠的就是这个）。

---

## 1.3 对比"写死程序"

| | 写死程序（裸 Agent） | 插件化 |
|---|---|---|
| 改一个功能 | 动整个文件、易连带出错 | 只改那个插件 |
| 增删功能 | 改代码、重新部署 | 装/卸插件 |
| 多人协作 | 互相踩脚 | 各写各的插件 |
| 复用 | 复制粘贴 | 直接装 |

**一句话**：**插件化 = 把"一大坨"变成"一堆积木"。** 这是从"能跑"迈向"能维护、能扩展"的第一步。
