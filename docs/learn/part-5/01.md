# 第1章 子代理（Subagent）

> 一个 Agent 单打独斗，遇到"大活"就容易上下文爆炸、顾此失彼。这一章讲怎么**派活给"分身"**——子代理。

---

## 1.1 为什么需要子代理

**大白话**：一个人干不完的大项目，会**分给同事**。Agent 也一样：主 Agent 把一个大任务**派给子代理**，子代理在自己的"小办公室"里干完，把结果交回来。

**专业**：**子代理（Subagent）** 是一个由主 Agent 派生的、**独立上下文**的 Agent 实例。价值有三：

| 价值 | 说明 |
|---|---|
| **上下文隔离** | 子代理的中间过程不污染主对话 |
| **并行** | 多个子代理同时干不同活 |
| **分工** | 各司其职（检索的、写作的、审核的） |

**关键**：子代理**不是为了炫技**——它的核心价值是**把"中间过程的噪声"挡在主上下文之外**。

---

## 1.2 fork vs spawn 的区别

**大白话**：派子代理有两种方式：

- **fork（分叉）**：子代理**继承**主对话的上下文——"你带着我们聊过的内容去干"。
- **spawn（新建）**：子代理**全新开始**，不继承——"你从零去干，我给你任务说明"。

**专业**：

| | fork | spawn |
|---|---|---|
| 上下文 | 继承父对话 | 全新 |
| 适合 | 需要共享背景 | 独立、纯净的活 |
| 风险 | 可能继承偏见 | 可能缺背景 |

> **重要**：**审计/独立评估类任务必须用 spawn**——继承上下文的"审计"会带偏见，等于自审。这一点在真实项目里非常关键。

---

## 1.3 上下文隔离：不继承全部记忆

**大白话**：子代理不该看到主对话的**全部**内容。给它**刚好够用的**信息就行。

**专业**：**上下文隔离**是子代理的核心设计。派生时只注入：**任务说明 + 必要背景 + 约束**，而不是整个对话历史。这样：

- 子代理**专注**、不被无关信息干扰；
- 主上下文**不膨胀**；
- 敏感信息**不扩散**。

---

## 1.4 派活与收结果（结构化返回）

**大白话**：派活要**说清楚**，收活要**结构化**——别让它回来讲一堆，要它交一份"标准报告"。

**专业**：子代理返回**结构化结果**（如 JSON：结论 + 证据 + 产物路径），主 Agent 才好整合。**"产物必须落盘、返回路径"**——这样即使子代理上下文丢了，成果还在。

```ts
// 示意：派活 + 结构化回收
const result = await spawnSubagent({
  task: '检索近三年马铃薯氮素诊断的高光谱研究，输出 5 篇关键文献',
  schema: { papers: [{ title: 'string', doi: 'string', why: 'string' }] },
})
```

**要点**：**未落盘的信息要标注**（如"【待办】"），避免"子代理说做了、实际没留痕"。
