# 第3章 认识工具（Tool）—— 它的手

> 本章你将会：看懂"函数调用"是怎么回事，掌握工具的"三要素"，并亲手写出第一个能读文件的工具。最后有个验收清单，做完就算过关。

上一章我们让模型会"开口说话"了，但它有个天生的局限：**它只会"想"和"说"，不会真的"做事"。** 你让它读一个文件、算一组数字、查一下当天天气——它做不到，因为它没有"手"。这一章，我们就给它装上一只手：**工具（Tool）**。

工具是 Agent 系统的"手"，也是让模型从"聊天机器人"升级成"能干活的人"的关键。学会了这一章，后面的循环才能跑起来。

---

## 3.1 什么是函数调用（Function Calling） {#sec-1}

**大白话**：模型自己不会跑你的代码，但它**很会指挥**。你给它一张"工具清单"，它在思考时发现自己需要某种能力（比如读文件），就会"开口要"：*我要调用 `read_file` 这个工具*。你（或你的程序）收到这个**请求**，真的去执行，再把**结果**喂回给模型。

这条链路就是一个闭环：

```
模型说"我想用 read_file，读 notes.md"
        ▼
你的程序真的去读文件，把内容拿回来
        ▼
把结果交给模型，它接着想
```

**专业**：函数调用（Function Calling，也叫 tool use / 工具调用）是让 LLM 在对话中**请求调用一个外部函数**的机制。**模型本身不执行代码**，它只输出一个**结构化的调用意图**（工具名 + 参数）；真正的执行由你的宿主程序完成，再把返回结果作为消息回填给模型。

一个"调用请求"长这样（模型想读文件的意图）：

```json
{
  "name": "read_file",
  "arguments": { "path": "notes.md" }
}
```

关键在于：**模型负责"决定要不要、用哪个、参数填什么"，你的程序负责"真的把它做出来"。** 各司其职。

---

## 3.2 工具三要素 {#sec-2}

要让模型能**正确**"指挥"一个工具，你得给它足够的信息。一个工具至少有三样：

| 要素 | 大白话 | 说明 |
|---|---|---|
| **名称 name** | 名字 | 唯一标识，如 `read_file`。模型靠它**点名**要用哪个工具。 |
| **描述 description** | 说明书 | 一句话说清"这工具能干嘛、什么时候该用"。**描述写得好坏，直接决定模型会不会用对。** |
| **参数 schema** | 怎么填单子 | 它需要哪些入参、各是什么类型、要什么、返回什么。模型据此填参数。 |

**大白话**：**名称是"名字"，描述是"说明书"，参数 schema 是"填单模板"。** 少了一样，模型都容易用错——尤其描述，写含糊了模型要么不用、要么错用。

> 这背后有个专业概念：**schema（模式/结构描述）**。它是给"机器看的说明书"，用特定的语法（如 JSON Schema）告诉模型"这个函数接受什么、返回什么"。你给的信息越清楚，模型越不容易出错。

一个工具的完整定义（示意写法）

```ts
// 示意：不同宿主定义方式略有差异，DSH 用 defineTool，核心是四块
export const readFileTool = defineTool({
  name: 'read_file',                                        // ① 名称
  description: '读取指定路径的文件内容并返回。当你需要查看工作区里的某个文件时使用。', // ② 描述
  parameters: {                                             // ③ 参数 schema
    type: 'object',
    properties: {
      path: { type: 'string', description: '要读取的文件路径，相对或绝对路径皆可。' },
    },
    required: ['path'],
  },
  async handler({ path }) {                                 // ④ 真正的处理函数
    const fs = require('fs/promises')
    const content = await fs.readFile(path, 'utf8')
    return { ok: true, content }
  },
})
```

> 记住四个字母 **N-D-P-H**：**N**ame、**D**escription、**P**arameters、**H**andler。这就是一个工具的全部。

## 3.3 写第一个工具（动手） {#sec-3}

把上面这套知识落成一个**能跑**的工具，分三步：

**第1步 · 定义工具对象**：写清名称 / 描述 / 参数 schema。
**第2步 · 写处理函数**：真正执行，并**加参数校验 + 错误处理**。工具不是"一定成功"——文件可能不存在、路径可能越界，处理函数要懂得"失败了也好好说话"。
**第3步 · 挂进工具列表**：把它挂到模型可用的工具列表里，模型才知道有它（下一步循环时才能被调用）。

> **两个关键点（新手最常踩的坑）**
> - **参数校验**：不要假设参数一定合法。模型填的参数可能缺、可能是错的类型。
> - **错误处理**：工具失败时，**要让模型知道"为什么失败"**，而不是静默出错、或抛个异常让整个程序崩溃。返回 `{ ok: false, error: '...' }` 让模型据此调整，比崩溃强得多。

一个**带校验 + 错误处理**的读文件工具：

```ts
export const readFileTool = defineTool({
  name: 'read_file',
  description: '读取指定路径文件内容；文件不存在时返回错误提示。',
  parameters: {
    type: 'object',
    properties: { path: { type: 'string', description: '要读取的文件路径' } },
    required: ['path'],
  },
  async handler({ path }) {
    // 参数校验：先确认 path 是有效字符串
    if (!path || typeof path !== 'string') {
      return { ok: false, error: '缺少有效的 path' }
    }
    // 错误处理：真实执行，出问题不崩溃，把原因交给模型
    try {
      const fs = require('fs/promises')
      const content = await fs.readFile(path, 'utf8')
      return { ok: true, content }
    } catch (e) {
      return { ok: false, error: `读取失败：${e.message}` }
    }
  },
})
```

**把它挂进工具列表**（示意）：

```ts
const toolList = [readFileTool]   // 模型可用的工具 = 一个列表
```

> 后续章节会讲：模型是怎么"看到"这个列表、选中 `read_file`、并把结果回填的——那就是核心循环（第4章）。

**动手练**：试着照上面的样子，**再写一个工具**，比如 `list_files`（列出一个目录下的文件名）或 `count_words`（统计一段文字的单词数）。要求：名称/描述/参数齐全，带参数校验 + 错误处理。

## 验收清单（做完才算过关） {#sec-4}

- [ ] 能写出一个工具（读文件），含 **名称 / 描述 / 参数 schema / 处理函数** 四块。
- [ ] **参数校验 + 错误处理**齐全——工具失败时不崩溃、能告诉模型原因。
- [ ] 把它**挂进工具列表**后，模型能在合适时机调用它。
- [ ] 能说出：**为什么"描述"写得好坏会影响模型用不用的对**。

**追问**（答不上来就回看 3.2）：模型参数传了 `path`，但文件不存在，你的工具应该返回什么？直接抛异常让程序崩？还是返回 `{ ok:false, error:'...' }`？为什么后者更好？
