# 第2章 调模型（LLM Provider）—— 它的脑子

> 本章你将学会：把"调模型"这件事封装成一个**统一入口（Provider）**，换模型时不用改上层代码；并掌握几个关键参数。

上一章我们备好了"上下文"（要递进去的那叠纸）。这一章，我们把它交给"脑子"——模型。

---

## 2.1 为什么要有统一入口

**大白话**：市面上的大模型有很多家（DeepSeek、OpenAI、Anthropic……），每家的调用接口**各有各的写法**。如果你在业务代码里到处直接写某家的接口，等哪天换模型，就要满地改代码。

**解决办法**：**封一个统一入口**——业务代码只说"请给我一个回复"，具体用哪家、怎么调，交给这个入口去办。

**专业**：这叫 **Provider 抽象**（供应商抽象）。定义一个统一接口（如 `chat(messages, options)`），不同模型各自实现；上层只依赖接口，不依赖具体厂商。换模型 = 换一个实现，业务代码不动。

---

## 2.2 最小模型调用

**大白话**：一次调用，就是"把 messages 发过去，把回复收回来"。

**专业**：调用 chat completions 接口，请求体里带 `model`（用哪颗脑子）和 `messages`（那叠纸），响应里取 `choices[0].message`。

```ts
// 一个极简的 Provider 实现（示意，以你实际服务为准）
type Msg = { role: 'system' | 'user' | 'assistant'; content: string }

async function chat(messages: Msg[], opts: { model?: string; temperature?: number } = {}) {
  const res = await fetch(`${process.env.LLM_BASE_URL}/chat/completions`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${process.env.LLM_API_KEY}`,
    },
    body: JSON.stringify({
      model: opts.model ?? 'deepseek-chat',
      messages,
      temperature: opts.temperature ?? 0.3,
    }),
  })
  const data = await res.json()
  return data.choices[0].message   // { role:'assistant', content:'...' }
}
```

> **安全提醒**：API Key 放**环境变量**（或 `.env` 并加入 `.gitignore`），**绝不写进代码、绝不提交到 Git**；CI 里用 repository secrets 注入。密钥一旦进了提交历史，很难彻底清除。

请求里主要带什么：

| 字段 | 作用 |
|---|---|
| `model` | 用哪个模型 |
| `messages` | 上下文（那叠纸） |
| `temperature` | 随机性（见 2.3） |
| `tools`（后续章节加） | 可调用的工具清单 |

## 2.3 关键参数

### 2.3.1 模型名（model）

选哪颗"脑子"。不同模型在**能力、速度、价格**上差别很大。做 Agent 时，常常"贵的用于规划、便宜的用于执行"（第5部分会展开）。

### 2.3.2 温度（temperature）

**大白话**：温度 = 随机性旋钮。
- **低（0~0.3）**：更确定、更稳，适合**要准确**的活（改代码、算数）。
- **高（0.7+）**：更发散、更有创意，适合**要灵感**的活（写文案、想点子）。

**Agent 默认建议偏低**——你要它"可靠干活"，不是"天马行空"。

### 2.3.3 最大输出（max_tokens）与多轮

- **max_tokens**：限制一次回复的长度，防止它"写个没完"。
- **多轮**：每次调用都要**把历史带上**（第1章 1.3.2），否则失忆。
