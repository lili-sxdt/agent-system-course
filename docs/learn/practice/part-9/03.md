# 例3 · 发布后：反馈与审计

> 目标：发布不是终点。**收集反馈 + 独立审计**，才知道「哪些地方要用的人难受、哪里有坑」。

<!-- 双向导航: 回主线 -->
> 📚 **先用主线打底**：这一练对应 **[主线 第9部分](/learn/part-9/01)**——建议先读主线概念，再动手做。

## L1 收反馈：用户真的用了吗 {#sec-1}

用户觉得不好用的地方，往往是你没想到的。**主动收集，别等用户来骂**。

```
反馈三渠道：
□ 日志：哪种任务失败最多？（数据说话）
□ 用户：哪个步骤觉得卡/不想要？（体验说话）
□ 社区：群里被问最多的问题？（说明哪没讲清）
```

> **反馈要分类**：是「不好用」（体验）、「不能用」（bug）、还是「没讲清」（文档）。三类改法不同。

## L2 反馈闭环：回到正确环节 {#sec-2}

反馈**要有去处**，不能「收到就完」——要判断它该回到哪一步修。

```text
反馈「读文件老是失败」
  → 排查：是工具错（L2 能力层）？还是提示词没让用对（L1 编排）？
  → 定位到能力层 → 修工具 → 再发小版本
```

> **关键**：别只「打补丁」，要问「这一步设计对不对」。反馈是**改进入口**，不是抱怨。

## L3 独立审计：别自己审自己 {#sec-3}

重要改动，让**另一个视角**来挑刺——自己容易「看不见自己的错」。

```text
自审：改完说「我觉得没问题」 —— 容易自我确认(有盲区)
独立审计：别人看你的改动，问「这里会不会崩」——更客观

→ 大版本 / 安全相关改动，一定要独立审计
```

> **为什么独立**：自己长期看这段代码，会有「思维定式」，反而看不见隐患。换个视角 = 多一道保险。

## 变体练习（举一反三） {#sec-4}

1. **设计一份反馈收集表**：想收集哪些信息。
2. **把一条反馈闭环到对应环节**：它该修在哪层。
3. **给一个重要改动做一次独立审计**：请别人/换个视角看。

## 通用套路：收反馈 + 闭环 + 独立审计 {#sec-5}

**发布后是「成长循环」**：**收反馈**（日志/用户/社区）→ **闭环**（定位到正确环节修）→ **独立审计**（换视角防盲区）。**自嗨式发布没有生命力**——懂得「让用户说话」，系统才会越用越好。
