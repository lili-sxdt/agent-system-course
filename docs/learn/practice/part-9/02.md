# 例2 · 回滚：出问题能退回去

> 目标：上线后发现坏了，要能**快速退回上一个可用版本**，而不是「坏着再改」。

<!-- 双向导航: 回主线 -->
> 📚 **先用主线打底**：这一练对应 **[主线 第9部分](/learn/part-9/01)**——建议先读主线概念，再动手做。

## L1 版本可回退：一份能用的备份 {#sec-1}

Git tag 就是「可用版本锚点」——坏了的版本，切回去即可。

```bash
git tag v0.3.0    # 打标签 = 记下"这版是好的"
# 出问题后：
git checkout v0.2.0   # 切回上一个可用版本
```

> **关键**：每次发布前打 tag，才知道「哪一版是好的、能退到哪」。

## L2 回滚预案：先想好怎么退 {#sec-2}

**上之前先想「怎么退」**，不是出事后才慌。

```text
问题：v0.3.0 读取中文路径失败
回滚：切到 v0.2.0 再发布（把 tag 指回上一个可用 commit）
回滚顺序：
  1. 确认坏在 v0.3.0（不在下游）
  2. 把发布指向 v0.2.0
  3. 通知用户你退回了
  4. 再慢慢修，别在坏版本上硬撑
```

> **回滚是「止损」，不是「修复」**。先退回可用版让用户能继续用，再从容修 bug。

## L3 回滚配合可观测 {#sec-3}

日志与回滚是搭档：**日志告诉你「坏在哪」**，回滚帮你「先退回去」。

```
warn  [v0.3.0] session.create  session=s-1  error=读取中文路径失败
  → 立即回滚到 v0.2.0（用户能继续用）
  → 修复 v0.3.0 的问题后再发 v0.4.0
```

> **回滚不是失败**，是成熟的工程动作。**发现问题 → 退回去 → 修好 → 再前进**，一个健康的节奏。

## 变体练习（举一反三） {#sec-4}

1. **给 v0.2.0 打 tag**，模拟「出问题退回去」。
2. **写一份回滚预案**：什么情况退、怎么退、通知谁。
3. **用日志定位**：怎么知道该回滚哪个版本。

## 通用套路：先想怎么退 + 快速回滚 + 修复再进 {#sec-5}

**回滚三原则**：①**打 tag**（先锚定可用版）；②**预案先行**（上之前就想好怎么退）；③**止损优先**（先退回可用版，再从容修）。**回滚是工程常态，不是失败**——会退，才敢大胆往前走。
