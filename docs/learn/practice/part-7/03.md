# 例3 · 版本与发布

> 目标：Agent 系统会**不断演进**——版本号、变更记录、打标签，让"改了啥、能不能上"清清楚楚。

## L1 版本号：语义化语义版本 {#sec-1}

语义化（Semantic Versioning）：`主.次.补丁`——规则简单、机器可读。

| 升级 | 什么时候 |
|---|---|
| 主版本 `1.0.0 → 2.0.0` | **不兼容**改动（API 变了、破坏性） |
| 次版本 `1.2.0 → 1.3.0` | 新增功能（向后兼容） |
| 补丁 `1.2.0 → 1.2.1` | 修 bug（向后兼容） |

> **为什么重要**：用户/下游一看版本号就知道**要不要小心**。乱版本号 = 信任崩塌。

## L2 CHANGELOG：这次改了啥 {#sec-2}

每次发布，写清"改了啥、影响谁"：

```markdown
## [1.3.0] - 2026-08-18
### 新增
- `llm.call` 支持流式返回
### 修复
- 修复中文路径读取失败
### 变更
- `readTool` 默认返回 `utf8`
```

> **面向读者写**：你的下游会是"用户 / 协作者 / 别的开发者"，写他们关心的事，不是你的开发流水账。

## L3 发布流程：打 tag + 可用 {#sec-3}

```bash
git tag v0.3.0            # 打版本标签
git push --tags
```

> **版本号放哪**：`package.json` 的 `version` + 根目录 `CHANGELOG.md`，两处一致。**发布前跑一遍测试**，发布即"当前这个 commit 是能用的"。

## 变体练习（举一反三） {#sec-4}

1. **打一个 `v0.3.0` tag**，写 `CHANGELOG`。
2. **加一条兼容性说明**：`v2.0.0` 破坏性，怎么迁移。
3. **把测试当发布门**：测试不过不发布。

## 通用套路：语义化 + CHANGELOG + tag 三件套 {#sec-5}

**版本三件套**：①**语义化版本**（主.次.补丁，规则清晰）；②**CHANGELOG**（面向读者的变更记录）；③**Git tag**（每个能用的版本一个标签）。配合"发布前跑测试"，发布才有公信力。
