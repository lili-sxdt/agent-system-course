# 例1 · 让系统长大：分层架构

> 目标：小系统的「能跑」不等于「能长大」。**把职责分清楚**，才能加功能不加混乱。

## L1 先有个「分工」 {#sec-1}

把 Agent 拆成几层，各管各的事：

```
┌─────────────────────────────┐
│ 应用层   （谁在用：CLI / Web）│
├─────────────────────────────┤
│ 编排层   （跑循环、调度工具）│
├─────────────────────────────┤
│ 能力层   （工具 / 技能 / 插件）│
├─────────────────────────────┤
│ 模型层   （API 调用、流式）  │
└─────────────────────────────┘
```

> **一次只管一层**：加一个工具，只碰能力层，不改编排层。

## L2 依赖要「向内」 {#sec-2}

**上层依赖下层，下层绝不依赖上层**——这是分层的铁律。

```ts
// ✗ 坏：工具层回传界面消息（反向依赖）
// ✓ 好：工具只返回数据，界面由应用层拼
tool: async (ctx) => ({ data: await fs.readFile(p, 'utf8') })
```

> **为什么**：下层一旦知道「上面是谁」，就再也拆不开、换不了。

## L3 模块尺寸：能独立替换 {#sec-3}

**一个模块一个职责、一个入口**，想换实现只动一个地方。

```ts
// 模型层 —— 只暴露一个接口
export interface LLM {
  chat(messages: Msg[], opts?: ChatOpts): Promise<Reply>
}
// 想换模型？换一个实现这个接口的东西就行
```

> **检验**：能不能「不翻别处」就替换一个模块？能 → 职责清晰；不能 → 耦合太深。

## 变体练习（举一反三） {#sec-4}

1. **把工具注册抽成独立模块**，编排层只调它的入口。
2. **给模型层换一个 mock 实现**，验证应用层不用改。

## 通用套路：分层要「单向依赖 + 单一职责」 {#sec-5}

**分层不是为了好看**，是为了「改一处不影响别处」。两条铁律：**依赖单向**（上层→下层）、**模块单一职责**（一个模块一件事）。能独立替换 = 好架构。
