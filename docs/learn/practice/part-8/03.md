# 例3 · 验收：交付前的检查

> 目标：发布前**按一张清单逐项过**，确认「要么真的行，要么明确知道哪里不行」——而不是「好像可以」。

## L1 验收清单：一条条勾 {#sec-1}

交付前对着清单过，而不是凭感觉「应该没问题」。

```
□ 核心任务能跑通（例：读文件→分析→回答）
□ 失败场景优雅处理（模型挂了、文件不存在）
□ 无越权行为（不乱写文件、不滥调工具）
□ 日志能定位问题
□ 简单任务不报错、速度可接受
□ 有一份「怎么用」的说明
```

> **清单要「可勾选」**：每一条能明确判断「过 / 没过」，不含糊。

## L2 验收标准：写清楚「什么算行」 {#sec-2}

**验收标准 = 可量化、可复现**，不能是「效果好一点」。

| 项目 | 标准（可测量） |
|---|---|
| 正确性 | 10 个固定任务全部完成 |
| 稳定性 | 连跑 50 次不崩 |
| 成本 | 单任务 token 消耗 < 阈值 |
| 延迟 | 单任务 < 30s |
| 安全 | 越权访问全部被拒 |

> **把「好」翻译成数字**：验收才有依据，用户才信你。「很流畅」无法验收，「<30s 且 50 次不崩」可以。

## L3 对抗式验收：故意找茬 {#sec-3}

自己当**挑剔用户**，专门试「最不该成功」的场景：

```
1. 让它读不存在的文件 —— 应优雅报错，不崩
2. 让它越权删文件 —— 应拒绝
3. 用极强的恶意输入 —— 应不照做
4. 并发跑多个任务 —— 应不互相干扰
```

> **验收不是证明「它能行」，而是逼自己「找出它会在哪崩」**。找不出 → 才敢上。

## 变体练习（举一反三） {#sec-4}

1. **写一份你项目的验收清单**，尽量可勾选。
2. **把「流畅」翻译成 3 条可测标准**。
3. **跑一次「故意找茬」**：列出 3 个它可能崩的场景。

## 通用套路：清单 + 量化标准 + 故意找茬 {#sec-5}

**验收三件套**：①**检查清单**（逐项可勾选）；②**量化标准**（把「好」翻译成数字）；③**故意找茬**（专门踩最危险的场景）。**验收通过 ≠ 完美，而是「已知边界、风险可控」**。
