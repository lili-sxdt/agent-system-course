# 第5章 编码规范与评审

> 最后一块。代码不光要"能跑"，还要**别人看得懂、敢改**。这一章讲规范与评审。

---

## 5.1 命名 / 类型 / 注释

**大白话**：

- **命名**：名字要说人话（`readFile` 而不是 `rf`）；
- **类型**：能标类型就标（TypeScript 的强项），让错误在编译期就暴露；
- **注释**：解释"**为什么**"，而不是"是什么"（代码本身已说明"是什么"）。

**专业**：

```ts
// 好：说清"为什么"
// 这里必须原子写：避免写一半崩溃导致配置文件损坏
await atomicWrite(path, data)
```

**要点**：**规范的价值是"降低别人的理解成本"**，不是"看起来整齐"。

---

## 5.2 代码评审清单

**大白话**：提交代码前，过一遍"检查清单"。

**专业**：一份实用清单：

- [ ] 功能对不对？有没有测？
- [ ] 边界/异常处理了吗？
- [ ] 命名/类型/注释清楚吗？
- [ ] 有没有引入安全风险（路径穿越、密钥硬编码）？
- [ ] 会不会破坏已有功能（回归）？
- [ ] 文档/CHANGELOG 同步了吗？

**要点**：**评审不是"挑刺"，是"一起把质量守住"**。独立评审（非自审）尤其关键——自己审自己容易漏。

---

## 5.3 从"能跑"到"敢维护"

**大白话**：能跑只是及格线；**敢让别人接手改**，才算真的好。

**专业**：可维护性的标志：**结构清晰、测试覆盖、文档同步、命名一致、错误可追、版本可回退**。这也正是"可发布 v0.1"的工程底座。

---

## 验收清单

- [ ] 能说出命名/类型/注释的**三条原则**。
- [ ] 能背出代码评审清单的**主要项**。
- [ ] 能说出可维护性的**几个标志**。
- [ ] 理解"独立评审"为什么比自审有效。

**追问**（答不上来就回看 5.2）：为什么"自己审自己的代码"容易漏问题？独立评审补上了什么？
