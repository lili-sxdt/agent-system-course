# 第4章 版本管理与发布

> 系统要迭代，就得有**版本号**和**发布流程**。这一章讲怎么"有条不紊地改和发"。

---

## 4.1 语义化版本（semver） {#sec-1}

**大白话**：版本号 `主.次.补丁`（如 `1.2.3`），三位各有含义：

```
主版本.次版本.补丁版本
  1   .   2   .   3
```

| 位 | 什么时候 +1 | 含义 |
|---|---|---|
| **主版本** | 有不兼容的改动 | 用户要改代码才能升级 |
| **次版本** | 加了新功能（向后兼容） | 加东西，不破坏 |
| **补丁版本** | 修了 bug（向后兼容） | 小修 |

**专业**：**语义化版本（Semantic Versioning）** 让用户一眼知道"这次升级会不会弄坏我的东西"。**破坏性改动必须进主版本号。**

---

## 4.2 changelog 与标签（版本线） {#sec-2}

**大白话**：每一版改了什么，要**记下来**，别让用户猜。

**专业**：

- **CHANGELOG**：按版本记录"新增/修复/破坏性变更"；
- **Git 标签（tag）**：给每次发布打标签（`v1.2.3`），对应一个确定的代码状态；
- **质量门 tag**：通过质量门时打标签（如 `gate-<环节>-<裁决>-<日期>`）。

**要点**：**版本号 + changelog + tag** 三件套，让"每个版本"都可追溯、可回退。

---

## 4.3 发布流程与质量门 {#sec-3}

**大白话**：发布不能"随手推"，要过几道关。

**专业**：**发布流程**典型步骤：

```
① 跑质量门（测试/lint/build 全过）
② 定版本号（按 semver）
③ 更新 CHANGELOG
④ 打 tag
⑤ 触发 CI 自动构建发布
⑥ 发布后监控
```

**要点**：**质量门是"发布的闸门"**——不过门，不许发。这正是本课程/科研协议里反复强调的"产物必须过审计门"的同一套思想。
