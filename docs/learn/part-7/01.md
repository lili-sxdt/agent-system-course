# 第1章 项目结构规范

> 系统能跑、能用了，接下来要让它**像个正经项目**。第一步：**结构规范**——东西放对地方，别人（和未来的你）才找得到。

---

## 1.1 包怎么划分 {#sec-1}

**大白话**：一个能力，一个包。别把所有功能塞进一个巨型文件。

**专业**：**按职责分包**（第2部分"插件化"的落地）。典型划分：

```
packages/
├── core/           # 核心循环、上下文、会话
├── tools/          # 各种工具
├── skills/         # 技能
├── sandbox/        # 安全与权限
├── llm/            # 模型适配
└── cli/            # 命令行入口
```

**要点**：**一个包只干一类事**，对外通过明确接口交互。这样可测试、可复用、可独立演进。

---

## 1.2 目录约定与命名 {#sec-2}

**大白话**：大家都按同一套规矩放文件，谁进来都知道东西在哪。

**专业**：约定示例：

| 目录 | 放什么 |
|---|---|
| `src/` | 源码 |
| `tests/` | 测试 |
| `docs/` | 文档 |
| `scripts/` | 可复用脚本 |
| `examples/` | 示例 |

**命名**：文件小写 + 连字符（`read-file.ts`），或按团队约定统一。**一致性比"哪个更好"更重要。**

---

## 1.3 "系统资产" vs "用户产物" {#sec-3}

**大白话**：**系统自己用的东西**（脚本、模板、测试）和**用户产出的东西**（数据、图、报告）**别混在一起**。

**专业**：

| | 系统资产 | 用户产物 |
|---|---|---|
| 例子 | 可复用脚本、模板、测试 | 课题数据、图、手稿 |
| 位置 | `research-assistant/`（或 `packages/`） | `projects/<课题>/` |
| 原则 | 可复用、跨项目 | 属于某个具体项目 |

**要点**：**混在一起 = 找不到、也管不清**。这条在真实项目里（包括这套课程的工作区）是被反复强调的硬规则。
