# 第6章 再发布 v0.2

> 改好了、测过了，现在把它**发出去变成 v0.2**。这一章讲怎么"发得稳、说得清、退得回"。

---

## 6.1 semver 决策

**大白话**：这次改动，版本号该怎么变？

**专业**：按第七部分 4.1 的规则：

| 改动性质 | 版本变化 | 例子 |
|---|---|---|
| 修 bug、不改接口 | 补丁 `0.1.1` | 修了个崩溃 |
| 加功能、向后兼容 | 次版本 `0.2.0` | 新增一个工具 |
| 破坏性改动 | 主版本（v0 阶段常表现为 `0.2.0` 里的大改） | 改了工具接口 |

**要点**：**破坏性改动必须让用户"看得见"**——别悄悄改坏别人的用法。

---

## 6.2 changelog 与迁移指南

**大白话**：告诉用户"这版改了啥、怎么升级"。

**专业**：

- **CHANGELOG**：新增 / 修复 / **破坏性变更**（重点标出）；
- **迁移指南**：破坏性改动要给出"老写法 → 新写法"的对照。

```md
## [0.2.0] - 2026-09-08
### 新增
- 支持多模型切换
### 破坏性变更
- `run()` 参数由位置参数改为对象；迁移：`run('x')` → `run({ task: 'x' })`
```

**要点**：**破坏性变更 + 迁移指南 = 对用户的尊重**。

---

## 6.3 发布流程与自动化

**大白话**：发布别手动一步步来，交给**流水线**。

**专业**：**CI/CD**：

```
lint → test → build → publish
```

打 tag 触发自动发布；自动化能减少人为失误。

> **【做】** 真正跑一次完整发布流水线——包括"打 tag → CI 自动发布 → 验证包能装"。

---

## 6.4 回滚与监控

**大白话**：万一 v0.2 有问题，要能**立刻退回 v0.1**；发完要**盯着看**。

**专业**：

- **回滚预案**：npm **不允许撤回已发布版本**（`npm unpublish` 仅 24 小时内且无下游依赖时可用，风险高、不推荐）。正确做法：`npm deprecate` 标记问题版本 + 发布修复版（如 `0.1.1`），并用 dist-tag 把 `latest` 指回稳定版（`npm dist-tag add pkg@0.1.0 latest`）；
- **灰度/预发布**：先小范围试，再全量；
- **发布后监控**：看日志/指标，出 bug 出热修。

> **【做】经验段**：真正"翻车又回滚"一次，比你读十遍"要回滚预案"都管用。
