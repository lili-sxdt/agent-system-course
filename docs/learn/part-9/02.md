# 第2章 收集与分类反馈

> 发出去了，接下来最关键的问题是：**有人在用吗？用得怎么样？哪里卡住了？**

---

## 2.1 反馈渠道怎么搭 {#sec-1}

**大白话**：给用户开几个"能说话的口子"——提 issue、发讨论、填问卷、写邮件。

**专业**：**反馈渠道**：

| 渠道 | 适合 |
|---|---|
| **Issue** | bug、功能请求（可追踪） |
| **Discussion** | 用法讨论、经验分享 |
| **埋点/日志** | 客观数据（用了哪些功能、哪步失败） |
| **问卷/访谈** | 深度反馈 |

**要点**：**主观反馈（用户说的）+ 客观数据（实际用的）** 要结合看——用户说的未必等于实际发生的。

---

## 2.2 反馈分类 {#sec-2}

**大白话**：一堆反馈混在一起没法处理，先**分类**：

| 类型 | 处理方式 |
|---|---|
| **Bug** | 修（优先） |
| **需求** | 排优先级，可能进下一版 |
| **误解** | 改文档，不用改代码 |
| **环境问题** | 补文档 / 加兼容 |

**专业**：给每条反馈打**标签 + 优先级 + 复现模板**。**复现模板**能大幅降低沟通成本（"你做了什么、期望什么、实际什么"）。

**要点**：**别把"用户误解"当 bug 修**——先分清类型，再动手。

---

## 2.3 从反馈提炼"下一版做什么" {#sec-3}

**大白话**：反馈很多，但资源有限。**排个优先级**，决定哪些进 v0.2。

**专业**：优先级可按"**影响面 × 严重度 × 实现成本**"排。列出：

- **进 v0.2**（高优先）；
- **进 v0.3**（重要但不急）；
- **砍掉**（不做，并说明原因）。

**要点**：**明确"不做什么"**——不然需求会无限膨胀，v0.2 永远发不出来。

---

## 验收清单 {#sec-4}

- [ ] 能说出**至少四种反馈渠道**及适用场景。
- [ ] 能对反馈**分类**（bug/需求/误解/环境）。
- [ ] 能说出优先级排序的**三个维度**。
- [ ] 知道要明确"不做什么"。

**追问**（答不上来就回看 2.2）：用户说"你这不是 bug 吗"，但其实是他没看文档。你会改代码还是改文档？为什么先分清类型很重要？
