# 第3章 验证

> 反馈来了，但"用户说的"不等于"真的"。这一章讲怎么**验证**：确认问题是真的、确认改动是对的。

---

## 3.1 复现问题 {#sec-1}

**大白话**：先把 bug **复现出来**——能稳定重现，才谈得上修。

**专业**：**复现三件套**：

- **最小复现示例**（能触发问题的最简代码/操作）；
- **环境快照**（系统、版本、配置）；
- **日志/轨迹**（出问题时的现场）。

**要点**：**复现不了，就别急着改**——否则你修的可能根本不是那个问题。

---

## 3.2 回归与兼容 {#sec-2}

**大白话**：改完这个，别把别的弄坏。

**专业**：

- **回归测试**：跑一遍已有测试，确认没破坏旧功能；
- **兼容性**：跨 OS / Node 版本 / 不同配置都要试。

> **【做】经验段**：很多 bug 是**环境相关**的——在你机器上好了、别人机器上没好。**只能跨环境真验才知道。**

---

## 3.3 安全与性能复核 {#sec-3}

**大白话**：改动可能引入新风险，也可能拖慢系统。

**专业**：

- **安全**：依赖扫描、漏洞检查、权限边界是否被绕过；
- **性能**：内存 / CPU / 响应时间，改前改后**对比**。

---

## 3.4 验收标准 {#sec-4}

**大白话**：怎么算"真的修好了"？

**专业**：重新对照"**可发布 7 标准**"逐项验，并区分：

- **真修好了**：有测试覆盖、能复现验证；
- **看起来修好了**：表面没了，实际还在。

**要点**：**"看起来修好了"是最大的陷阱**——要能证明，别靠感觉。

---

## 验收清单 {#sec-5}

- [ ] 能说出**复现三件套**（最小示例/环境/日志）。
- [ ] 知道改动后要跑**回归 + 兼容**。
- [ ] 能说出安全/性能复核看什么。
- [ ] 能区分"真修好"和"看起来修好"。

**追问**（答不上来就回看 3.1）：用户报了一个 bug，但你复现不出来。你该直接改，还是先做点别的？为什么？
