# 第4章 维护

> 发布不是终点，而是"长期养着"的起点。这一章讲**维护**：让系统在时间里不腐坏。

---

## 4.1 依赖治理 {#sec-1}

**大白话**：你的系统靠着一堆"别人的轮子"（依赖）。轮子会旧、会坏、会有漏洞。

**专业**：

- **升级**：定期更新依赖（但要测兼容）；
- **锁定**：用 lockfile 锁定版本，保证可复现；
- **监控**：留意依赖的**许可证变更**和安全公告。

**要点**：**依赖不治，迟早拖垮**——尤其安全漏洞，可能一夜之间让你"不合格"。

---

## 4.2 技术债务与评审 {#sec-2}

**大白话**：为了赶进度写的"凑合代码"，就是**技术债务**——早晚要还。

**专业**：

- **定期重构**：清理死代码、拆分大函数；
- **评审常态化**：每次改动都过评审（第7部分 5.2），别攒着。

**要点**：**债务要"定期还"**，别等到积重难返。

---

## 4.3 文档同步 {#sec-3}

**大白话**：**改了代码，就要改文档**。文档和代码不一致，比没有文档更坑。

**专业**：

- 功能变了 → 更新 README / API 文档；
- 行为变了 → 更新示例；
- 每次发布 → 更新 CHANGELOG。

**要点**：**文档是"给未来的自己和用户"的**，不是一次性作业。

---

## 4.4 安全与密钥 {#sec-4}

**大白话**：密钥（API Key）**永远不进仓库**；有漏洞赶紧补。

**专业**：

- **密钥管理**：环境变量注入、密钥轮换；
- **依赖审计**：定期扫描漏洞；
- **最小权限**：能用低权限就别用高权限。

**要点**：**密钥泄露是"灾难级"问题**——一旦提交进 Git 历史，很难彻底清除。

---

## 验收清单 {#sec-5}

- [ ] 能说出依赖治理的**三件事**（升级/锁定/监控）。
- [ ] 能说出技术债务要"定期还"。
- [ ] 知道**改了代码就要同步文档**。
- [ ] 能说出密钥管理的**底线**（不进仓库、可轮换）。

**追问**（答不上来就回看 4.4）：不小心把 API Key 提交进了 Git 仓库，为什么"删掉那个文件再提交"往往不够？
