# 第4章 命令行入口（Cmdline）

> 不是所有场景都要图形界面。这一章讲 Agent 的**命令行入口**——让它在终端里、在脚本里、在自动化流水线里都能用。

---

## 4.1 用命令行调用你的 Agent {#sec-1}

**大白话**：一行命令，跑一个任务。像这样：

```bash
my-agent "把 results/ 里的数据整理成表格"
```

**专业**：**CLI（命令行接口）** 把 Agent 暴露成一个可执行命令。它接受参数（任务、选项），执行后输出结果。**CLI 是"脚本化"和"自动化"的入口。**

**要点**：CLI 的输出要**既能给人看，也能给程序读**（如支持 `--json`）。

---

## 4.2 常用子命令与参数 {#sec-2}

**大白话**：一个命令，可以有多个"子命令"——像 `git` 有 `git add`、`git commit`。

**专业**：常见的子命令设计：

| 子命令 | 作用 |
|---|---|
| `run <task>` | 执行一个任务 |
| `session list/new/rm` | 管理会话 |
| `skill list/install` | 管理技能 |
| `config get/set` | 查看/修改配置 |

**参数设计原则**：
- **`--help` 永远能用**（自我说明）；
- **默认值合理**（第2部分 5.2 的优先级）；
- **错误提示清楚**（告诉用户怎么改）。

---

## 4.3 与 CI / 自动化集成 {#sec-3}

**大白话**：把 Agent 塞进"自动流水线"——比如每次提交代码后，自动跑一遍检查。

**专业**：CLI 要能被 CI 调用，就要：

- **退出码规范**（成功 0、失败非 0）；
- **非交互模式**（别卡在等待输入）；
- **输出可解析**（JSON 格式）；
- **幂等/可重入**（重复跑不产生副作用）。

**要点**：**"能在 CI 里跑"是 Agent 从"人用"到"系统用"的分水岭。**

---

## 验收清单 {#sec-4}

- [ ] 能说清 **CLI 的价值**（脚本化、自动化）。
- [ ] 能设计几个常见**子命令**（run / session / skill / config）。
- [ ] 能说出参数设计的三个原则（--help / 合理默认 / 清楚报错）。
- [ ] 能说出 CLI 进 CI 的**四个要求**（退出码/非交互/可解析/可重入）。

**追问**（答不上来就回看 4.3）：如果一个 CLI 在 CI 里"卡住等你输入"，会发生什么？为什么"非交互模式"这么重要？

---

## 第六部分小结 {#sec-5}

到这里，你的 mini-harness 已经能被**人用**（前端）、被**程序调**（协议/SDK）、被**脚本和流水线用**（CLI）了。它不再是一个"孤立的程序"，而是一个"**能被接入的产品**"。下一部分，我们让它**专业**：工程化与规范。
