# 第1章 协议与 SDK

> 前面你的 Agent 只能"自己跑"。这一章开始，让它能被**别的程序调用**——这就需要一个"约定的说话方式"（协议）和一套"方便别人用的封装"（SDK）。

---

## 1.1 JSON-RPC：进程间通信的约定 {#sec-1}

**大白话**：两个程序要对话，得**约好怎么说**。JSON-RPC 就是一套简单的约定：你发一个"请求"（说要调用哪个方法、带什么参数），我回一个"响应"（结果或错误）。

**专业**：**JSON-RPC** 是一种基于 JSON 的轻量远程调用协议。请求含 `method`、`params`、`id`；响应含 `result` 或 `error`，用同一个 `id` 对应上。

```json
// 请求
{ "jsonrpc": "2.0", "id": 1, "method": "session.send", "params": { "text": "你好" } }
// 响应
{ "jsonrpc": "2.0", "id": 1, "result": { "ok": true } }
```

**要点**：**`id` 让"请求"和"响应"配对**——并发多请求时不会串。

---

## 1.2 SDK 分层：minimal / app / protocol {#sec-2}

**大白话**：SDK（开发工具包）是把"底层协议"包装成"好用的函数"，让别人不用自己拼 JSON。

**专业**：DSH 的 SDK 大致分三层：

| 层 | 作用 |
|---|---|
| **protocol** | 定义消息类型与协议契约 |
| **minimal** | 最精简的客户端/服务端实现 |
| **app** | 面向应用的高层封装（开箱即用） |

**要点**：**分层是为了"按需使用"**——只想连一下用 minimal，要完整能力用 app。

---

## 1.3 你的系统对外暴露什么 {#sec-3}

**大白话**：你得想清楚——**别人能用你的系统做什么**？发消息？查会话？取消任务？

**专业**：**对外接口（API）** 应遵循"**最小暴露**"：只开必要的方法，且每个方法有明确权限。别把内部实现全抖出来。

**经验**：先定义"**能力清单**"，再定接口——**能力决定接口，而不是反过来**。

## 验收清单 {#sec-4}

- [ ] 能说清 **JSON-RPC 的请求/响应结构**，以及 `id` 的作用。
- [ ] 能说出 SDK 的**三层**及各自定位。
- [ ] 知道对外接口要遵循**最小暴露**原则。

**追问**（答不上来就回看 1.1）：两个请求同时发出，响应回来顺序打乱了，你怎么知道哪个响应对应哪个请求？
