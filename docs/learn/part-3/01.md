# 第1章 技能（Skill）

> **分水岭开始**。前面都在"理解系统"，从这一章起，你开始**写能被系统认出来、并真正生效的东西**。第一个：**技能（Skill）**。

---

## 1.1 为什么 Agent 需要"说明书"

**大白话**：模型不是万能的。你希望它"按你们公司的规范写周报""用你导师认可的统计方法"，光靠临时对话说不清、也记不住。于是你写一份**说明书**放进系统，模型需要时就照着做——这就是**技能**。

**专业**：**Skill** 是一份**结构化的知识/流程文档**，在合适时机被加载进上下文，指导模型如何完成某类任务。它**不是提示词**，而是**可复用、可版本管理、按需加载**的能力包。

### 1.1.1 不是提示词，是可控的知识块

提示词是"一次性的临时指令"；技能是"**沉淀下来、谁都能用**的规范"。前者易失、难维护，后者可归档、可复用。

### 1.1.2 何时加载、何时不加载

**关键**：技能**不是永远塞进上下文**（那会撑爆上下文）。它靠 **`whenToUse`** 决定"什么时候该被加载"。**按需加载**是技能设计的精髓。

---

## 1.2 SKILL.md 的 frontmatter

一个技能就是一个 `SKILL.md`，开头有一段 **frontmatter**（用 `---` 包起来的元信息）：

```md
---
name: report-writing
description: 把研究结果写成规范的 IMRaD 论文结构。
whenToUse: 用户需要写论文、报告、摘要，或要求结构化写作时。
---

# 正文：具体怎么做的说明……
```

| 字段 | 大白话 | 作用 |
|---|---|---|
| **name** | 技能名 | 唯一标识 |
| **description** | 一句话说明 | 让人（和模型）知道这技能干嘛 |
| **whenToUse** | 什么时候用 | **决定它何时被加载**（最关键） |

> **`whenToUse` 写得好不好，直接决定这个技能会不会在该用的时候被用上。** 写太窄，用不上；写太宽，乱加载。

---

## 1.3 正文怎么组织

正文就是"**教模型怎么做这类任务**"，三条原则：

1. **指令清楚**：一步一句，别含糊。
2. **可执行**：写成"能照着做的动作"，不是"你要认真"。
3. **可验证**：最好给出"做完应该是什么样"的验收标准。

```md
## 步骤
1. 先确认研究对象与目标期刊。
2. 按 IMRaD 搭骨架：引言/方法/结果/讨论。
3. 每个结论附证据（数据、DOI）。

## 验收
- [ ] 结构完整
- [ ] 每个结论有证据
- [ ] 无过度声称
```

---

## 1.4 从写到被调用的完整链路

```
你写 SKILL.md → 系统登记（ctx.skill）→ 需要时按 whenToUse 加载 → 进入上下文 → 模型照着做
```

**大白话**：你写的东西**不需要"接进代码"**——写好、登记，系统自己会在对的时机用上它。**这就是"自己能编写"的第一个成就感。**

---

## 1.5 技能 vs 普通提示词

| | 普通提示词 | 技能（Skill） |
|---|---|---|
| 生命周期 | 一次对话 | 长期沉淀、可复用 |
| 加载 | 每次都塞 | 按 `whenToUse` 按需加载 |
| 维护 | 散落各处 | 归档、可版本管理 |
| 协作 | 各写各的 | 谁都能装、能用 |
