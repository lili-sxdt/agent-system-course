# Chapter 1: Requirements and Architecture Design

> The capstone project begins. But **do not rush to code** — first be clear about "what to do, what not to do, and how to split it up." This chapter is the "blueprint before breaking ground."

---

## 1.1 Define the goal and boundaries {#sec-1}

**In plain terms**: answer three questions first:

1. **What should it do?** (e.g., "help me turn the Markdown files in a folder into one summary report")
2. **What should it not do?** (e.g., "no web search," "do not touch files outside the workspace")
3. **What counts as done?** (there is an artifact; it passes acceptance)

**Technical**: **requirement boundaries** determine all subsequent design. **"What not to do" matters as much as "what to do"** — unclear boundaries let the system balloon without limit.

**Key**: write a **one-page requirements note**: goal, non-goals, acceptance criteria.

---

## 1.2 Draw the architecture diagram {#sec-2}

**In plain terms**: draw the system's "parts" and "how they connect," so it is clear at a glance.

![mini-harness system architecture](../../../assets/architecture.svg)

**Technical**: the architecture diagram should at least make the **five elements** clear:

```
[user / frontend]
     │
     ▼
[session / context] ──► [core loop] ──► [model]
     ▲                │
     │                ▼
     └────────── [tools] ──► [sandbox / permissions] ──► [filesystem]
                      │
                      ▼
                 [logging / monitoring]
```

**Key**: **draw first, code later.** A diagram exposes "what is missing and what is tangled."

---

## 1.3 Module division and dependencies {#sec-3}

**In plain terms**: turn the parts in the diagram into "packages," and state clearly who depends on whom.

**Technical**: following the package-splitting principle from Part 7:

```
core (loop / context / session)
 ├── depends on llm (model adapters)
 ├── depends on tools (tools)
 └── depends on sandbox (permissions)
cli / web (entry) → depends on core
```

**Key**: **dependencies must be one-directional and acyclic.** core should not depend back on cli. **Messy dependencies pull the system apart.**

---

## Checklist {#sec-4}

- [ ] Can write a **one-page requirements note** (goal / non-goals / acceptance criteria).
- [ ] Can draw an architecture diagram containing the **five elements**.
- [ ] Can make a **module division** and guarantee **one-directional, acyclic dependencies**.

**Follow-up** (look back at §1.1 if stuck): why is "being clear about what not to do" as important as "what to do"? What happens if you do not write "non-goals"?
