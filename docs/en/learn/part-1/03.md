# Chapter 3: Getting to Know Tools — Its Hands

> In this chapter you will: understand what "function calling" is, master the "three elements" of a tool, and write your first tool that reads a file. There is a checklist at the end — do it and you pass.

In the previous chapter we got the model to "speak," but it has an inherent limit: **it can only "think" and "say"; it cannot really "do."** Ask it to read a file, compute a set of numbers, or check today's weather — it cannot, because it has no "hands." In this chapter we give it one hand: **a tool (Tool).**

A tool is the agent's "hands," and the key that upgrades a model from "chatbot" to "a person who can get things done." Once you learn this chapter, the loop later can run.

---

## 3.1 What function calling is {#sec-1}

**In plain terms**: the model cannot run your code itself, but it is **very good at directing**. You hand it a "tool list"; while thinking, it finds it needs some ability (say, reading a file) and "asks for it": *I want to call the `read_file` tool.* You (or your program) receive this **request**, actually execute it, and **feed the result** back to the model.

This pipeline is a closed loop:

```
model says "I want to use read_file, read notes.md"
        ▼
your program actually reads the file and returns the content
        ▼
hand the result to the model, and it thinks on
```

**Technical**: function calling (also called tool use) is the mechanism that lets an LLM **request the invocation of an external function** within a conversation. **The model itself does not execute code** — it only outputs a **structured call intent** (tool name + arguments); the actual execution is done by your host program, which then feeds the result back to the model as a message.

A "call request" looks like this (the model's intent to read a file):

```json
{
  "name": "read_file",
  "arguments": { "path": "notes.md" }
}
```

The key is: **the model is responsible for "whether to call, which one, and what arguments"; your program is responsible for "actually doing it."** Each does its own job.

---

## 3.2 The three elements of a tool {#sec-2}

For the model to "direct" a tool *correctly*, you must give it enough information. A tool needs at least three things:

| Element | In plain terms | Explanation |
|---|---|---|
| **name** | the name | a unique identifier, e.g., `read_file`. The model uses it to **name** which tool to use. |
| **description** | the manual | one sentence on "what this tool does and when to use it." **How well you write the description directly determines whether the model uses it correctly.** |
| **parameters (schema)** | how to fill the form | which inputs it needs, their types, what it takes and returns. The model fills arguments accordingly. |

**In plain terms**: **the name is the "name"; the description is the "manual"; the parameter schema is the "form template."** Missing any one, the model is likely to misuse it — especially the description: if it is vague, the model will either not use it or misuse it.

> There is a technical concept behind this: **schema (a structural description)**. It is a "manual for machines," using a specific syntax (such as JSON Schema) to tell the model "what this function accepts and returns." The clearer the information you give, the less likely the model makes a mistake.

A complete tool definition (illustrative):

```ts
// Illustrative: host conventions differ; DSH uses defineTool; the core is four parts
export const readFileTool = defineTool({
  name: 'read_file',                                  // ① name
  description: 'Reads the content of a file at the given path. Use when you need to view a file in the workspace.', // ② description
  parameters: {                                       // ③ parameter schema
    type: 'object',
    properties: {
      path: { type: 'string', description: 'The file path to read; relative or absolute.' },
    },
    required: ['path'],
  },
  async handler({ path }) {                           // ④ the actual handler
    const fs = require('fs/promises')
    const content = await fs.readFile(path, 'utf8')
    return { ok: true, content }
  },
})
```

> Remember the four letters **N-D-P-H**: **N**ame, **D**escription, **P**arameters, **H**andler. That is all there is to a tool.

## 3.3 Write your first tool (hands-on) {#sec-3}

Turn the above into a **runnable** tool, in three steps:

**Step 1 · define the tool object**: write out name / description / parameter schema.
**Step 2 · write the handler**: actually execute, with **parameter validation + error handling**. A tool is not "always successful" — the file may not exist, the path may be out of bounds; the handler must "speak well even when it fails."
**Step 3 · mount it into the tool list**: attach it to the model's available tools, so the model knows it exists (so it can be called in the loop next).

> **Two key points (the most common beginner pitfalls)**
> - **Parameter validation**: never assume arguments are valid. The model may omit an argument or give the wrong type.
> - **Error handling**: when a tool fails, **let the model know why it failed**, rather than failing silently or throwing an exception that crashes the whole program. Returning `{ ok: false, error: '...' }` and letting the model adjust is far better than crashing.

A read-file tool **with validation + error handling**:

```ts
export const readFileTool = defineTool({
  name: 'read_file',
  description: 'Reads the content of a file at the given path; returns an error if the file is missing.',
  parameters: {
    type: 'object',
    properties: { path: { type: 'string', description: 'The file path to read' } },
    required: ['path'],
  },
  async handler({ path }) {
    // parameter validation: first confirm path is a valid string
    if (!path || typeof path !== 'string') {
      return { ok: false, error: 'missing a valid path' }
    }
    // error handling: execute for real; on failure, don't crash — hand the cause to the model
    try {
      const fs = require('fs/promises')
      const content = await fs.readFile(path, 'utf8')
      return { ok: true, content }
    } catch (e) {
      return { ok: false, error: `read failed: ${e.message}` }
    }
  },
})
```

**Mount it into the tool list** (illustrative):

```ts
const toolList = [readFileTool]   // the model's available tools = a list
```

> Later chapters cover how the model "sees" this list, selects `read_file`, and feeds the result back — that is the core loop (Chapter 4).

**Try it**: following the same pattern, **write another tool**, such as `list_files` (list filenames in a directory) or `count_words` (count words in some text). Requirement: name/description/parameters complete, with parameter validation + error handling.

## Checklist (done and you pass) {#sec-4}

- [ ] Can write a tool (read file) with all four parts: **name / description / parameter schema / handler**.
- [ ] Has **parameter validation + error handling** — it does not crash on failure and tells the model the reason.
- [ ] After **mounting it into the tool list**, the model can call it at the right moment.
- [ ] Can say **why the quality of the "description" affects whether the model uses it correctly.**

**Follow-up** (look back at §3.2 if stuck): the model passed a `path`, but the file does not exist. What should your tool return? Throw and crash the program? Or return `{ ok:false, error:'...' }`? Why is the latter better?
