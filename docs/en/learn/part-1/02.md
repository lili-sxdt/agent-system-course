# Chapter 2: Calling the Model (LLM Provider) — Its Brain

> In this chapter you will learn to wrap "calling the model" into a **unified entry point (Provider)** so that switching models does not require changing upper-layer code — and to master a few key parameters.

In the previous chapter we prepared the "context" (the stack of papers). In this one, we hand it to the "brain" — the model.

---

## 2.1 Why a unified entry point {#sec-1}

**In plain terms**: there are many large-model vendors (DeepSeek, OpenAI, Anthropic…), and each has a **different calling interface**. If you hardcode one vendor's interface all over your business code, then the day you switch models you will be editing code everywhere.

**The fix**: **wrap a unified entry point** — your business code only says "give me a reply"; which vendor and how to call it is the entry point's job.

**Technical**: this is a **Provider abstraction**. Define a unified interface (such as `chat(messages, options)`); each model provides an implementation; the upper layer depends only on the interface, not on a specific vendor. Switching models = swapping an implementation, leaving business code untouched.

---

## 2.2 Minimal model call {#sec-2}

**In plain terms**: one call is "send the messages over, get a reply back."

**Technical**: call the chat completions endpoint; the request body carries `model` (which brain) and `messages` (the stack of papers); take `choices[0].message` from the response.

```ts
// A minimal Provider implementation (illustrative; use your actual service)
type Msg = { role: 'system' | 'user' | 'assistant'; content: string }

async function chat(messages: Msg[], opts: { model?: string; temperature?: number } = {}) {
  const res = await fetch(`${process.env.LLM_BASE_URL}/chat/completions`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${process.env.LLM_API_KEY}`,
    },
    body: JSON.stringify({
      model: opts.model ?? 'deepseek-chat',
      messages,
      temperature: opts.temperature ?? 0.3,
    }),
  })
  const data = await res.json()
  return data.choices[0].message   // { role:'assistant', content:'...' }
}
```

> **Security note**: keep the API key in an **environment variable** (or an `.env` added to `.gitignore`), **never hardcode it or commit it to Git**; in CI inject it via repository secrets. Once a key enters commit history, it is very hard to remove completely.

What the request mainly carries:

| Field | Purpose |
|---|---|
| `model` | which model to use |
| `messages` | context (the stack of papers) |
| `temperature` | randomness (see §2.3) |
| `tools` (added in later chapters) | the list of callable tools |

## 2.3 Key parameters {#sec-3}

### 2.3.1 Model name (`model`)

Which "brain" you pick. Models differ greatly in **capability, speed, and price**. When building an agent, a common practice is "use a pricey model for planning and a cheap one for execution" (expanded in Part 5).

### 2.3.2 Temperature

**In plain terms**: temperature = the randomness knob.
- **Low (0–0.3)** : more deterministic and stable; suited for **precision work** (editing code, arithmetic).
- **High (0.7+)** : more divergent and creative; suited for **inspiration work** (writing copy, brainstorming).

**For an agent, keep it low by default** — you want it "reliably working," not "wildly imaginative."

### 2.3.3 Max output (`max_tokens`) and multi-turn

- **`max_tokens`**: limits the length of one reply, preventing it from "writing on and on."
- **Multi-turn**: every call must **carry the history** (Part 1 §1.3.2), otherwise it amneses.
