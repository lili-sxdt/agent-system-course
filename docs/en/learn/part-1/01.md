# Chapter 1: Context — The Agent's Memory

> In this chapter you will understand what a model "sees" each turn, how context is assembled, how to write a system prompt, and the two most common beginner mistakes. This is the first building block of the foundation.

Part 0 introduced the agent's **five elements**, and the first is "context." In this chapter we take it apart and look at it closely.

---

## 1.1 What context is {#sec-1}

**In plain terms**: Imagine a person who is **blindfolded each turn and shown only a stack of papers**. Each turn they can see only the stack you hand them this time — what you wrote, what they replied last turn, the tool results, and the "rules" sheet on top. That stack of papers is **context**.

**Technical**: Context = the **entire message sequence** passed as input to the model in a single call. A model **has no memory** — everything it "knows" about "what happened before" comes from the stack you pass in this time.

### 1.1.1 What a model "sees" each turn

In one call, the model roughly sees:

- **system**: rules / persona ("who are you, what rules must you follow");
- **history**: the alternating past dialogue of user and assistant;
- **tool results**: content fed back after a tool call in the previous turn (e.g., a file you read).

### 1.1.2 Context = the sum of all visible information

Remember this formula:

```
context = system prompt + history dialogue + tool results (+ attachments / file snippets)
```

**Whatever you want the model to "know," you must put into this formula.** Anything not put in, the model does not know at all.

### 1.1.3 Example: why there is amnesia without context

Suppose that each time you send the model **only the current sentence**:

> Turn 1 you say: "Please read config.json for me."
> Turn 2 you say: "Change it to 8080."

If in turn 2 you **did not carry the turn-1 dialogue**, the model is baffled: "Change what? Where?" — it is not dumb; it is that **you took away its memory**.

**So the essence of "remembering" is not that the model remembers, but that "you carry along what should be carried."** This point is key and will come up again when we discuss "compaction."

## 1.2 The system prompt {#sec-2}

### 1.2.1 What it does: set persona, rules, and boundaries

The system prompt is the text placed **at the front and present every turn**; it tells the model:

- **persona**: are you a "research assistant" or "customer service";
- **rules**: answer concisely / confirm before acting;
- **boundaries**: what not to do (e.g., "do not fabricate data").

### 1.2.2 How to write it clearly, specifically, and actionably

Three tips:

1. **Be specific**: do not write "answer well"; write "answer in no more than 3 sentences."
2. **Be actionable**: write actions the model can follow, not abstract attitudes.
3. **Give examples**: for key formats, provide one or two "input → expected output" samples.

### 1.2.3 System prompt vs. user message

**In plain terms**: **the system prompt is the boss's rule** (always present, high priority); **the user message is this turn's specific request.** A rule should not be casually overturned by a single request.

**Technical**: most models follow system with higher priority than user. Therefore **put key constraints in system**, and temporary requests in user.

## 1.3 Message structure (multi-turn) {#sec-3}

### 1.3.1 Three roles: user / assistant / system

| Role | Who says it | Purpose |
|---|---|---|
| `system` | you (developer) | set rules, persona |
| `user` | the user | make a request |
| `assistant` | the model | the model's reply (including tool-call intent) |

### 1.3.2 How multiple turns become one request

A full turn's `messages` roughly looks like this:

```ts
const messages = [
  { role: 'system', content: 'You are a rigorous assistant; if unsure, say so.' },
  { role: 'user', content: 'Please read the port in config.json.' },
  { role: 'assistant', content: 'Sure, I will read it.' },      // last turn's model reply
  { role: 'user', content: 'Did you read it?' },                 // this turn's user message
]
```

**Key**: history messages are **in chronological order**, and system is always first.

### 1.3.3 Common mistakes

- **Wrong order**: system placed later, or history out of order → the model is confused.
- **Role confusion**: labeling a user message as assistant, or a model message as user → the model cannot tell who said what.
- **Forgetting history**: sending only the current sentence in a multi-turn task → the model "amneses."
