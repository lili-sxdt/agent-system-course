# Chapter 2: Tools

> A skill is "knowledge it can talk about"; a tool is "an action it can perform." This chapter upgrades the "three elements" from Part 1 §3 (getting to know tools) into an engineering form that is **registrable, maintainable, and testable.**

---

## 2.1 `defineTool`: how to define a tool {#sec-1}

**In plain terms**: a tool = **name + description + parameters + handler** (remember N-D-P-H?). Use `defineTool` to wrap it into a standard object, so the system can register it and the model can call it.

```ts
import { defineTool } from './tool'

export const listFilesTool = defineTool({
  name: 'list_files',
  description: 'Lists filenames in the given directory. Use when you need to know which files a folder contains.',
  parameters: {
    type: 'object',
    properties: { dir: { type: 'string', description: 'directory path' } },
    required: ['dir'],
  },
  async handler({ dir }) {
    const fs = await import('fs/promises')
    try {
      return { ok: true, files: await fs.readdir(dir) }
    } catch (e: any) {
      return { ok: false, error: e.message }
    }
  },
})
```

---

## 2.2 Input / output / description conventions {#sec-2}

**Inputs**: declare type, required, and meaning with JSON Schema. **Every parameter needs a `description`** — the model relies on it to fill the value correctly.

**Outputs**: use a **uniform structure**, recommended `{ ok: boolean, ... }`: data on success, `error` on failure. **A uniform structure helps the model understand results and helps your loop handle them.**

**Description**: one sentence stating "**what it does + when to use it.**" Do not just write "read a file"; write "reads the content of the specified file; use it when you need to inspect a file."

---

## 2.3 How to write a description the model "uses correctly" {#sec-3}

This is the most overlooked point and the one with the greatest impact:

- **State "when to use"**: the model relies on it to decide whether to call.
- **State "when not to use"** (if needed): to avoid misuse.
- **Do not describe internals**: the model does not care which library you use, only "what it takes and what it returns."

> **Counter-example**: `description: "process data"` — the model has no idea when to use it.
> **Good example**: `description: "Reads a CSV file into tabular data; use when the user asks to analyze a table file."`

---

## 2.4 Tool vs. skill {#sec-4}

| | Tool | Skill |
|---|---|---|
| essence | an action it **can do** | knowledge it **can talk about** |
| example | read a file, run a command | "how to write a weekly report" |
| when used | the model decides to execute | the model decides to consult |
| form | code + schema | Markdown |

**In one sentence**: **a tool does the doing; a skill guides the doing.** Only with both does an agent have hands and accumulated "experience."

---

## 2.5 A complete tool example + test {#sec-5}

A good tool must be **testable**. Write a minimal test:

```ts
// test (vitest): both normal and error paths return a uniform structure
import { expect, test } from 'vitest'
import path from 'node:path'
import os from 'node:os'

test('normal directory: returns a file list', async () => {
  const r = await listFilesTool.handler({ dir: '.' })
  expect(r.ok).toBe(true)
  expect(Array.isArray(r.files)).toBe(true)
})

test('missing directory: returns an error instead of throwing', async () => {
  const missing = path.join(os.tmpdir(), 'no-such-dir-' + Date.now())
  const r = await listFilesTool.handler({ dir: missing })
  expect(r.ok).toBe(false)
  expect(typeof r.error).toBe('string')
})
```

**Key**: **a failing tool must still "return gracefully,"** not throw and crash — so the loop in Part 1 §4 can catch it reliably.

## Checklist {#sec-6}

- [ ] Can write a tool with `defineTool` (N-D-P-H complete).
- [ ] The tool's **output is uniform** as `{ ok, ... }`, with `error` on failure.
- [ ] Can write a `description` that clearly states "when to use."
- [ ] Can write a **minimal test** for the tool (normal + error).

**Try it**: following this chapter's `listFilesTool`, write your own `read_file` tool (N-D-P-H complete + parameter validation + error handling), and add a test.

**Follow-up** (look back at §2.3 if stuck): two tool descriptions are "process data" and "read a CSV into a table; use when the user asks to analyze a table." Which will the model use correctly more often? Why?
