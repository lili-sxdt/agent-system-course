# Chapter 1: Skills

> **The watershed begins.** So far we have been "understanding the system." From this chapter on, you start **writing things the system recognizes and that actually take effect.** The first: a **skill.**

---

## 1.1 Why an agent needs a "manual" {#sec-1}

**In plain terms**: a model is not omniscient. You want it to "write weekly reports per your company's standard" or "use the statistical method your advisor approves." Ad-hoc conversation cannot state this clearly or retain it. So you write a **manual** into the system, and the model follows it when needed — that is a **skill.**

**Technical**: a **skill** is a **structured knowledge/procedure document** loaded into context at the right time to guide the model through a class of task. It is **not a prompt** but a **reusable, versionable, on-demand** capability package.

### 1.1.1 Not a prompt, but a controllable knowledge block

A prompt is a "one-off temporary instruction"; a skill is a "**distilled standard anyone can use.**" The former is easily lost and hard to maintain; the latter can be archived and reused.

### 1.1.2 When to load, when not to

**Key**: a skill is **not always stuffed into context** (that would blow up the context). It relies on **`whenToUse`** to decide "when it should be loaded." **On-demand loading is the essence of skill design.**

---

## 1.2 The frontmatter of SKILL.md {#sec-2}

A skill is a `SKILL.md` file whose top has a **frontmatter** (metadata wrapped in `---`):

```md
---
name: report-writing
description: Turn research results into a structured IMRaD paper.
whenToUse: When the user needs to write a paper, report, or abstract, or requests structured writing.
---

# Body: concrete how-to instructions…
```

| Field | In plain terms | Purpose |
|---|---|---|
| **name** | the skill's name | a unique identifier |
| **description** | a one-line explanation | lets people (and the model) know what it does |
| **whenToUse** | when to use it | **decides when it is loaded** (the most important) |

> **How well you write `whenToUse` directly determines whether the skill gets used when it should be.** Write it too narrow and it never triggers; too broad and it loads at random.

---

## 1.3 How to organize the body {#sec-3}

The body is "**teaching the model how to do this class of task**," with three principles:

1. **Clear instructions**: one step per line, no ambiguity.
2. **Actionable**: write actions to follow, not "be careful."
3. **Verifiable**: ideally give acceptance criteria for "what done looks like."

```md
## Steps
1. Confirm the study subject and target journal.
2. Build the skeleton per IMRaD: Introduction / Methods / Results / Discussion.
3. Attach evidence to every conclusion (data, DOI).

## Acceptance
- [ ] Structure complete
- [ ] Every conclusion has evidence
- [ ] No overclaiming
```

---

## 1.4 The full path from writing to being invoked {#sec-4}

```
you write SKILL.md → the system registers it (ctx.skill) → loaded by whenToUse when needed → enters context → the model follows it
```

**In plain terms**: what you write **does not need to be "wired into code"** — write it, register it, and the system uses it at the right time. **This is your first sense of achievement in "writing things yourself."**

---

## 1.5 Skill vs. ordinary prompt {#sec-5}

| | Ordinary prompt | Skill |
|---|---|---|
| lifetime | one conversation | long-term, reusable |
| loading | stuffed in every time | loaded on demand via `whenToUse` |
| maintenance | scattered | archived, versionable |
| collaboration | each writes their own | anyone can mount and use it |

---

## Checklist {#sec-6}

- [ ] Can state the **difference between a skill and a prompt**.
- [ ] Can write a `SKILL.md` **frontmatter** (name/description/whenToUse).
- [ ] Can say **why `whenToUse` is the most important** (it decides when to load).
- [ ] Can write a skill body that is "clear / actionable / verifiable."

**Try it**: write a `SKILL.md` for a task you know well (e.g., "organize an experimental data table"), with frontmatter + steps + acceptance.

**Follow-up** (look back at §1.1.2 if stuck): if a skill were **always stuffed into context**, what problems would arise?
