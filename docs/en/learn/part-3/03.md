# Chapter 3: Roles / Presets (Agent / Persona)

> A skill is "knowledge"; a tool is "action." This chapter covers the third thing you can write: a **persona (Persona / Preset)** — it defines an agent's **identity, tone, and boundaries.**

---

## 3.1 Structure and writing of persona / preset {#sec-1}

**In plain terms**: a persona is "who this agent is." It is usually a description placed in the **system prompt**, telling the model: your identity, your responsibilities, your code of conduct.

**Technical**: a **Persona** is a role definition injected into system; a **Preset** is "a whole bundle of configuration" — persona + model choice + available tools + default parameters. A preset lets "the same system" switch into "different roles."

```md
# Persona example
You are "Xiaodi," a research agent serving agricultural science / plant nutrition.

## Responsibilities
- Help the user through the full research cycle from topic selection to publication
- Every stage's output must pass the quality gate

## Guidelines
- Conclusions must have evidence (DOI / data / path)
- If unsure, say so; do not fabricate
```

---

## 3.2 How a persona affects behavior, boundaries, and tone {#sec-2}

A persona can influence three things at once:

| Dimension | How to write it | Effect |
|---|---|---|
| **behavior** | "confirm before acting" | the model is more cautious |
| **boundaries** | "do not fabricate data" | the model makes things up less |
| **tone** | "concise Chinese, professional but not stiff" | output style is controllable |

**Key**: **a persona is a "soft constraint," but a very effective one.** The more specific and actionable, the more the model complies.

---

## 3.3 Priority of identity vs. instruction {#sec-3}

**In plain terms**: the persona is a "long-term identity"; a user message is a "temporary request." **A user request should not casually override the persona's bottom line.**

**Technical**: the general priority is **system (persona/rules) > user (temporary request)**. So **put bottom-line rules in system**; do not rely on repeating them in every user message.

> Exception: an explicit user authorization ("allow it just this once…") can override non-bottom-line rules — but **safety/compliance bottom lines are not among them.**

---

## 3.4 A complete example {#sec-4}

```md
---
name: data-analyst
description: A rigorous data-analysis assistant
model: deepseek-chat
tools: [read_file, list_files, run_python]
---

You are "the data steward," a rigorous data-analysis assistant.

## Responsibilities
Organize the data the user provides into analyzable tables and give conclusions.

## Guidelines
- Look at the data first, then conclude; do not speculate
- Attach evidence to every conclusion (which table, which statistic)
- If unsure, say so and give a way to verify

## Output style
Give a one-sentence conclusion first, then the basis.
```

**See**: this preset fixes **persona + model + available tools + output style** — **configure once, reuse everywhere.**

- [ ] Can state how a persona affects **behavior / boundaries / tone**.
- [ ] Can explain the **priority of identity vs. user instruction**, and where the bottom line belongs.
- [ ] Can write a **preset** with persona + model + tools.

**Try it**: write a persona for your own scenario (e.g., "paper-polishing assistant"), with responsibilities, guidelines, and style sections.

**Follow-up** (look back at §3.3 if stuck): if "do not fabricate data" were written only in one user message, would it still hold in the next conversation? Where should it go?
