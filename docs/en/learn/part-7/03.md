# Chapter 3: Logging, Monitoring, and Error Handling

> Once the system is live, what do you do when something goes wrong? This chapter covers "**visible and resilient**" — logging, monitoring, and error handling.

---

## 3.1 Log levels and tailing {#sec-1}

**In plain terms**: the program must "keep a diary." But not everything — **log important things, and you can turn off trivia.**

**Technical**: **log levels**:

| Level | Purpose |
|---|---|
| `debug` | debugging detail (off by default) |
| `info` | normal milestones (startup, task completion) |
| `warn` | potential issues (recoverable) |
| `error` | something failed (needs attention) |

**Tailing**: watch the latest logs in real time, following along as it runs — most useful when diagnosing.

**Key**: logs must be **tail-able** (real-time) and **filterable by level** (so you are not drowned by debug).

---

## 3.2 Error handling and fallback {#sec-2}

**In plain terms**: errors are not the scary part; **crashing without knowing why is.** You want to "catch the error, explain the cause, and continue if possible."

**Technical**:

- **catch**: do not let an exception crash the whole system;
- **classify**: retryable (network) vs. non-retryable (bad argument);
- **fallback**: when the primary path fails, retreat to a "works but worse" option (e.g., switch models, skip a non-critical step);
- **report**: record the error to logs/monitoring.

```ts
try {
  return await primaryPath()
} catch (e) {
  log.warn('primary path failed, falling back', e)
  return await fallbackPath()
}
```

**Key**: **fallback is "graceful retreat," not "pretending nothing happened"** — it must be recorded and traceable.

---

## 3.3 Monitoring: milestones / health status {#sec-3}

**In plain terms**: you need to know at any moment "is the system alive, and how is it doing."

**Technical**: **monitoring** focuses on two categories:

- **health status**: is the process alive, is the port open, are dependencies available (health checks);
- **milestones**: key events (task start/complete/fail, model call counts, token consumption).

**Key**: **no monitoring = you learn about problems from user complaints.** With monitoring, you can find them proactively.
