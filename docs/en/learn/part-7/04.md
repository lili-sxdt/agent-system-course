# Chapter 4: Version Management and Release

> For the system to iterate, it needs a **version number** and a **release process.** This chapter covers how to "change and release in an orderly way."

---

## 4.1 Semantic versioning (semver) {#sec-1}

**In plain terms**: the version number is `major.minor.patch` (e.g., `1.2.3`), and each part has a meaning:

```
major . minor . patch
  1   .   2   .   3
```

| Part | When to +1 | Meaning |
|---|---|---|
| **major** | there is an incompatible change | users must change their code to upgrade |
| **minor** | a new feature is added (backward-compatible) | add things without breaking |
| **patch** | a bug is fixed (backward-compatible) | small fixes |

**Technical**: **semantic versioning** lets users see at a glance "will this upgrade break my stuff." **Breaking changes must go into the major version number.**

---

## 4.2 Changelog and tags (version line) {#sec-2}

**In plain terms**: what changed in each version must be **recorded**, not left for users to guess.

**Technical**:

- **CHANGELOG**: record "added / fixed / breaking changes" by version;
- **Git tag**: tag each release (`v1.2.3`), pointing to a specific code state;
- **quality-gate tag**: tag when a quality gate passes (e.g., `gate-<stage>-<verdict>-<date>`).

**Key**: the trio of **version number + changelog + tag** makes every version traceable and revertible.

---

## 4.3 Release process and quality gate {#sec-3}

**In plain terms**: you cannot "just push" a release; it must pass several gates.

**Technical**: typical **release process** steps:

```
① run the quality gate (tests/lint/build all pass)
② decide the version number (per semver)
③ update the CHANGELOG
④ tag it
⑤ trigger CI to build and publish automatically
⑥ monitor after release
```

**Key**: **the quality gate is the "gatekeeper of release"** — no pass, no publish. This is the same idea repeatedly emphasized in this course / the research protocol: "outputs must pass the audit gate."
