# Chapter 5: Coding Standards and Review

> The last piece. Code must not only "run" but also be **understandable and safe for others to change.** This chapter covers standards and review.

---

## 5.1 Naming / types / comments {#sec-1}

**In plain terms**:

- **naming**: names should speak plainly (`readFile`, not `rf`);
- **types**: annotate types whenever possible (a TypeScript strength), so errors surface at compile time;
- **comments**: explain "**why**," not "what" (the code already says what).

**Technical**:

```ts
// good: explains "why"
// must be an atomic write here: to avoid corrupting the config if it crashes mid-write
await atomicWrite(path, data)
```

**Key**: **the value of standards is "lowering others' cost of understanding,"** not "looking tidy."

---

## 5.2 Code review checklist {#sec-2}

**In plain terms**: before committing code, run through a "checklist."

**Technical**: a practical checklist:

- [ ] Is the functionality correct? Is it tested?
- [ ] Are boundaries/exceptions handled?
- [ ] Are naming/types/comments clear?
- [ ] Does it introduce security risks (path traversal, hardcoded keys)?
- [ ] Will it break existing functionality (regression)?
- [ ] Are docs/CHANGELOG updated?

**Key**: **review is not "nitpicking," it is "holding the quality line together."** Independent review (not self-review) is especially critical — reviewing your own code easily misses things.

---

## 5.3 From "runs" to "dare to maintain" {#sec-3}

**In plain terms**: running is just the passing grade; being **safe for others to take over and change** is what makes it genuinely good.

**Technical**: markers of maintainability: **clear structure, test coverage, synced docs, consistent naming, traceable errors, revertible versions.** This is also the engineering foundation of a "publishable v0.1."
