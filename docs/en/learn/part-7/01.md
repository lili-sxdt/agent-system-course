# Chapter 1: Project Structure Conventions

> The system runs and is usable; next we make it **look like a serious project.** The first step: **structure conventions** — put things in the right place, so others (and your future self) can find them.

---

## 1.1 How to split packages {#sec-1}

**In plain terms**: one capability, one package. Do not cram every feature into one giant file.

**Technical**: **split by responsibility** (the practical realization of "plug-in" from Part 2). A typical split:

```
packages/
├── core/           # core loop, context, sessions
├── tools/          # various tools
├── skills/         # skills
├── sandbox/        # security and permissions
├── llm/            # model adapters
└── cli/            # command-line entry
```

**Key**: **a package does only one class of thing** and interacts through a clear interface. This makes it testable, reusable, and independently evolvable.

---

## 1.2 Directory conventions and naming {#sec-2}

**In plain terms**: everyone places files by the same rules, so anyone walking in knows where things are.

**Technical**: an example convention:

| Directory | What goes in it |
|---|---|
| `src/` | source code |
| `tests/` | tests |
| `docs/` | documentation |
| `scripts/` | reusable scripts |
| `examples/` | examples |

**Naming**: lowercase filenames + hyphens (`read-file.ts`), or whatever the team agrees on. **Consistency matters more than "which is better."**

---

## 1.3 "System assets" vs. "user artifacts" {#sec-3}

**In plain terms**: **things the system itself uses** (scripts, templates, tests) and **things the user produces** (data, figures, reports) must **not be mixed together.**

**Technical**:

| | System assets | User artifacts |
|---|---|---|
| examples | reusable scripts, templates, tests | project data, figures, manuscripts |
| location | `research-assistant/` (or `packages/`) | `projects/<project>/` |
| principle | reusable, cross-project | belongs to a specific project |

**Key**: **mixing them = can't find anything and can't manage it.** This is a hard rule repeatedly emphasized in real projects (including this course's workspace).

---

## Checklist {#sec-4}

- [ ] Can state the principle of **splitting by responsibility** and a typical split.
- [ ] Can describe a set of **directory conventions** (src / tests / docs / scripts / examples).
- [ ] Can distinguish **system assets** from **user artifacts**, and knows they should be separated.

**Follow-up** (look back at §1.3 if stuck): if "reusable scripts" and "one project's data" were mixed in one folder, what trouble would you run into six months later?
