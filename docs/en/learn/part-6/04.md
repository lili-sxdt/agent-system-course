# Chapter 4: The Command-Line Entry (Cmdline)

> Not every scenario needs a graphical interface. This chapter covers the agent's **command-line entry** — so it can be used in a terminal, in a script, and in an automation pipeline.

---

## 4.1 Calling your agent from the command line {#sec-1}

**In plain terms**: one command, one task. Like this:

```bash
my-agent "organize the data in results/ into a table"
```

**Technical**: a **CLI (command-line interface)** exposes the agent as an executable command. It takes arguments (task, options) and prints the result. **The CLI is the entry point for "scripting" and "automation."**

**Key**: the CLI's output should be **both human-readable and machine-parsable** (e.g., support `--json`).

---

## 4.2 Common subcommands and arguments {#sec-2}

**In plain terms**: one command can have several "subcommands" — just as `git` has `git add` and `git commit`.

**Technical**: a common subcommand design:

| Subcommand | Purpose |
|---|---|
| `run <task>` | execute a task |
| `session list/new/rm` | manage sessions |
| `skill list/install` | manage skills |
| `config get/set` | view / modify configuration |

**Argument design principles**:
- **`--help` always works** (self-documenting);
- **sensible defaults** (the priority from Part 2 §5.2);
- **clear error messages** (tell the user how to fix it).

---

## 4.3 Integration with CI / automation {#sec-3}

**In plain terms**: put the agent into an "automated pipeline" — for example, run a check automatically after each commit.

**Technical**: for a CLI to be called by CI, it must:

- **follow exit-code conventions** (0 on success, non-zero on failure);
- **run in non-interactive mode** (do not hang waiting for input);
- **produce parsable output** (JSON format);
- **be idempotent / re-entrant** (running it repeatedly has no side effects).

**Key**: **"able to run in CI" is the dividing line between an agent "used by people" and "used by systems."**

## Checklist {#sec-4}

- [ ] Can state the **value of a CLI** (scripting, automation).
- [ ] Can design a few common **subcommands** (run / session / skill / config).
- [ ] Can state the three argument-design principles (--help / sensible defaults / clear errors).
- [ ] Can state the **four requirements** for a CLI in CI (exit code / non-interactive / parsable / re-entrant).

**Follow-up** (look back at §4.3 if stuck): if a CLI "hangs waiting for your input" in CI, what happens? Why is "non-interactive mode" so important?
