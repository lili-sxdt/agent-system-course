# Chapter 3: The Goal-Driven Loop

> An ordinary loop "stops at each step"; complex tasks span many steps, many turns, even many days. This chapter covers the **goal-driven loop**: letting an agent **keep advancing itself** toward a goal.

---

## 3.1 Self-advancement on long tasks {#sec-1}

**In plain terms**: some jobs cannot be stated or finished in one go — for example, "read these 30 papers closely and write a review." You need to give it **a goal** so it **pushes forward turn after turn on its own**, rather than you prodding it at every step.

**Technical**: the **goal-driven loop** is an execution mechanism that advances around a **persistent goal**. It records "what the goal is, how far it has gotten, what to do next," and **automatically decides whether to continue** at the end of each turn.

```ts
interface Goal {
  id: string
  objective: string      // the goal
  phase: 'active' | 'done' | 'blocked'
  rounds: number         // rounds advanced
  maxRounds: number
}
```

**Key**: **the goal must be written to disk** (persisted), so that even if interrupted midway, it can be picked up again.

---

## 3.2 Judging complete / blocked {#sec-2}

**In plain terms**: when is it "done"? When is it "stuck"?

**Technical**:

- **complete**: the goal is **truly achieved** (there is an artifact, it passes acceptance), not "looks like it was done."
- **blocked**: the same obstacle **fails to be resolved for several consecutive rounds** — you cannot cry "stuck" the moment you hit difficulty.

| State | Criterion |
|---|---|
| complete | goal achieved, with evidence |
| blocked | the same condition unchanged for N consecutive rounds |
| continue | there is still work to advance |

**Key**: **"complete" is judged by "goal achieved," not by "I tried my best."** This is especially important in automated systems.

---

## 3.3 Resume from a checkpoint / memory persistence {#sec-3}

**In plain terms**: if it breaks off halfway (shutdown, crash), **pick up from where it stopped** next time, rather than starting over.

**Technical**: **resuming from a checkpoint** is enabled by **persisted progress**: write the goal state, completed steps, and intermediate artifacts to disk; read them back on restart and continue. **This is the same idea as "session persistence" in Part 4** — only at a coarser granularity (per round / per stage).

```
[goal + progress written to disk] → interruption → restart → [read progress back] → continue from the checkpoint
```
