# Chapter 2: Workflows

> Some tasks cannot be handled by "one loop"; they require **several stages strung together.** This chapter covers how to organize multi-step work into a **workflow.**

---

## 2.1 What a workflow is {#sec-1}

**In plain terms**: a workflow = breaking a task into **stages** and running them in order (or in parallel). Like an assembly line: raw material → processing → inspection → packaging.

**Technical**: a **workflow** organizes a task into a structured process of **multiple stages**, each of which may be "one agent call" or "one tool call," with clear **input/output contracts** between stages.

```
[stage 1: retrieve] → [stage 2: filter] → [stage 3: extract] → [stage 4: summarize]
```

**Key**: the difference between a workflow and "one long loop" is that — **the workflow's structure is set by you, while the loop's path is chosen by the model.**

---

## 2.2 Stages and barriers {#sec-2}

**In plain terms**: stages sometimes need to "wait" — **wait until the previous stage is fully done before entering the next.** This "wait" is a barrier.

**Technical**: a **barrier** is a synchronization point between stages. With a barrier → continue only after all parallel tasks finish; without one → each proceeds independently (a pipeline, faster but more complex).

| | with barrier | without barrier (pipeline) |
|---|---|---|
| characteristics | tidy, simple | fast, but harder to manage |
| suited to | strong stage dependencies | independent tasks |

---

## 2.3 Parallel execution and result merging {#sec-3}

**In plain terms**: within one stage, several jobs can run **at the same time**; when done, **aggregate** the results.

**Technical**: **parallel execution** raises throughput; **result merging** (reduce) combines multiple outputs into one. Note the handling of **partial failure** — one failure should not drag down the whole batch.

```ts
// Illustrative: parallel + merge
const results = await parallel(tasks.map(t => () => runStage(t)))
const merged = results.filter(Boolean).flat()   // filter out failures, merge successes
```

**Key**: **allow partial failure** and **record which ones failed** — do not let one bad result ruin the batch.

---

## 2.4 Trade-off with "one long loop" {#sec-4}

**In plain terms**: if a simple loop can do it, do not reach for a workflow.

| | one long loop | workflow |
|---|---|---|
| structure | decided by the model | fixed by you in advance |
| controllability | low | high |
| flexibility | high | low |
| suited to | exploratory tasks | fixed processes |

**Rule of thumb**: **stable process → workflow; uncertain path → loop.** Do not over-orchestrate (echoing Anthropic's "start simple, add complexity as needed").
