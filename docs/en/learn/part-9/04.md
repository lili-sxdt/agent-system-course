# Chapter 4: Maintenance

> Release is not the end; it is the start of "long-term care." This chapter covers **maintenance**: keeping the system from decaying over time.

---

## 4.1 Dependency governance {#sec-1}

**In plain terms**: your system relies on a pile of "other people's wheels" (dependencies). Wheels get old, break, and acquire vulnerabilities.

**Technical**:

- **upgrade**: update dependencies periodically (but test compatibility);
- **lock**: pin versions with a lockfile to guarantee reproducibility;
- **monitor**: watch dependencies' **license changes** and security advisories.

**Key**: **leave dependencies unmanaged and they will drag you down** — especially security vulnerabilities, which can make you "non-compliant" overnight.

---

## 4.2 Technical debt and review {#sec-2}

**In plain terms**: "make-do code" written to rush a deadline is **technical debt** — it comes due sooner or later.

**Technical**:

- **refactor regularly**: remove dead code, split large functions;
- **make review routine**: every change goes through review (Part 7 §5.2); do not let it pile up.

**Key**: **debt must be "repaid regularly"**; do not wait until it is unmanageable.

---

## 4.3 Documentation sync {#sec-3}

**In plain terms**: **change the code, change the docs.** Docs that disagree with the code are worse than no docs.

**Technical**:

- feature changed → update the README / API docs;
- behavior changed → update the examples;
- every release → update the CHANGELOG.

**Key**: **docs are "for your future self and your users,"** not a one-off chore.

---

## 4.4 Security and keys {#sec-4}

**In plain terms**: an API key **never goes into the repository**; patch vulnerabilities promptly.

**Technical**:

- **key management**: inject via environment variables, rotate keys;
- **dependency audit**: scan for vulnerabilities regularly;
- **least privilege**: if a low-privilege option works, do not use a high-privilege one.

**Key**: **a key leak is a "disaster-level" problem** — once committed to Git history, it is very hard to erase completely.

---

## Checklist {#sec-5}

- [ ] Can state the **three things** of dependency governance (upgrade / lock / monitor).
- [ ] Can state that technical debt must be "repaid regularly."
- [ ] Knows that **changing code means syncing docs**.
- [ ] Can state the **bottom line** of key management (never in the repo, rotatable).

**Follow-up** (look back at §4.4 if stuck): you accidentally committed an API key to a Git repository. Why is "delete that file and commit again" often not enough?
