# Chapter 2: Collecting and Classifying Feedback

> It is out. The most critical questions now are: **is anyone using it? How is it going? Where do they get stuck?**

---

## 2.1 Setting up feedback channels {#sec-1}

**In plain terms**: open a few "ways to speak up" for users — file an issue, start a discussion, fill in a survey, send an email.

**Technical**: **feedback channels**:

| Channel | Suited to |
|---|---|
| **Issue** | bugs, feature requests (trackable) |
| **Discussion** | usage discussion, experience sharing |
| **instrumentation / logs** | objective data (which features are used, which step fails) |
| **survey / interview** | in-depth feedback |

**Key**: **subjective feedback (what users say) + objective data (what actually happens)** should be read together — what users say is not always what actually occurs.

---

## 2.2 Classifying feedback {#sec-2}

**In plain terms**: a pile of mixed feedback cannot be handled; **classify first**:

| Type | Handling |
|---|---|
| **bug** | fix (priority) |
| **feature request** | prioritize; may go into the next version |
| **misunderstanding** | fix the docs, not the code |
| **environment problem** | improve docs / add compatibility |

**Technical**: give each piece of feedback a **label + priority + reproduction template**. A **reproduction template** greatly reduces communication cost ("what you did, what you expected, what actually happened").

**Key**: **do not fix a "user misunderstanding" as a bug** — classify first, then act.

---

## 2.3 Distilling "what to do next" from feedback {#sec-3}

**In plain terms**: there is a lot of feedback but limited resources. **Prioritize** and decide what goes into v0.2.

**Technical**: priority can be ranked by "**impact × severity × implementation cost**." List:

- **into v0.2** (high priority);
- **into v0.3** (important but not urgent);
- **cut** (not doing it, with a stated reason).

**Key**: **be explicit about "what not to do"** — otherwise requirements balloon without limit and v0.2 never ships.

---

## Checklist {#sec-4}

- [ ] Can name **at least four feedback channels** and their suitable scenarios.
- [ ] Can **classify** feedback (bug / feature / misunderstanding / environment).
- [ ] Can state the **three dimensions** of priority ranking.
- [ ] Knows to be explicit about "what not to do."

**Follow-up** (look back at §2.2 if stuck): a user says "isn't this a bug?" but actually they did not read the docs. Do you change the code or the docs? Why is classifying first so important?
