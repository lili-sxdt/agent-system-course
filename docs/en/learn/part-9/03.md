# Chapter 3: Verification

> Feedback has arrived, but "what the user says" is not the same as "what is true." This chapter covers **verification**: confirming the problem is real and the fix is correct.

---

## 3.1 Reproducing the problem {#sec-1}

**In plain terms**: first **reproduce** the bug — only when it can be reliably recreated is it worth fixing.

**Technical**: the **reproduction trio**:

- **minimal reproduction** (the simplest code/action that triggers it);
- **environment snapshot** (OS, version, configuration);
- **logs / trajectory** (the scene at the time of the problem).

**Key**: **if you cannot reproduce it, do not rush to change anything** — otherwise you may be fixing the wrong problem.

---

## 3.2 Regression and compatibility {#sec-2}

**In plain terms**: after fixing this, do not break something else.

**Technical**:

- **regression testing**: run the existing tests to confirm old functionality is intact;
- **compatibility**: try across OS / Node versions / different configurations.

> **【do】Experience note**: many bugs are **environment-related** — fine on your machine, not on someone else's. **Only cross-environment verification reveals them.**

---

## 3.3 Security and performance re-check {#sec-3}

**In plain terms**: a change may introduce new risk or slow the system down.

**Technical**:

- **security**: dependency scanning, vulnerability checks, whether permission boundaries are bypassed;
- **performance**: memory / CPU / response time, **compare before and after**.

---

## 3.4 Acceptance criteria {#sec-4}

**In plain terms**: what counts as "truly fixed"?

**Technical**: re-check item by item against the "**7 publishability criteria**," and distinguish:

- **truly fixed**: covered by tests, verifiable by reproduction;
- **looks fixed**: gone on the surface, still there underneath.

**Key**: **"looks fixed" is the biggest trap** — you must be able to prove it, not rely on a feeling.

---

## Checklist {#sec-5}

- [ ] Can state the **reproduction trio** (minimal example / environment / logs).
- [ ] Knows that after a change you must run **regression + compatibility**.
- [ ] Can state what security/performance re-checks look at.
- [ ] Can distinguish "truly fixed" from "looks fixed."

**Follow-up** (look back at §3.1 if stuck): a user reports a bug, but you cannot reproduce it. Should you change the code directly, or do something else first? Why?
