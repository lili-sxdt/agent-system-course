# Chapter 6: Re-releasing v0.2

> Fixed and tested — now **ship it as v0.2.** This chapter covers how to "ship steadily, explain clearly, and roll back if needed."

---

## 6.1 Semver decision {#sec-1}

**In plain terms**: for this change, how should the version number move?

**Technical**: per the rules in Part 7 §4.1:

| Nature of change | Version change | Example |
|---|---|---|
| bug fix, no interface change | patch `0.1.1` | fixed a crash |
| new feature, backward-compatible | minor `0.2.0` | added a tool |
| breaking change | major (at v0, often a big change within `0.2.0`) | changed a tool interface |

**Key**: **breaking changes must be made "visible" to users** — do not quietly break someone's usage.

---

## 6.2 Changelog and migration guide {#sec-2}

**In plain terms**: tell users "what changed in this version and how to upgrade."

**Technical**:

- **CHANGELOG**: added / fixed / **breaking changes** (highlighted);
- **migration guide**: breaking changes must give an "old syntax → new syntax" comparison.

```md
## [0.2.0] - 2026-09-08
### Added
- Support for switching among multiple models
### Breaking changes
- `run()`'s argument changed from positional to an object; migrate: `run('x')` → `run({ task: 'x' })`
```

**Key**: **breaking change + migration guide = respect for your users.**

---

## 6.3 Release process and automation {#sec-3}

**In plain terms**: do not release step by step manually; hand it to a **pipeline**.

**Technical**: **CI/CD**:

```
lint → test → build → publish
```

Tagging triggers automatic publishing; automation reduces human error.

> **【do】** Actually run a complete release pipeline once — including "tag → CI auto-publish → verify the package installs."

---

## 6.4 Rollback and monitoring {#sec-4}

**In plain terms**: if v0.2 has a problem, you must be able to **fall back to v0.1 immediately**; after release, **watch it.**

**Technical**:

- **rollback plan**: npm **does not allow withdrawing a published version** (`npm unpublish` is only available within 24 hours and with no downstream dependents; high-risk, not recommended). The correct approach: `npm deprecate` to flag the problematic version + publish a fixed version (e.g., `0.1.1`), and use a dist-tag to point `latest` back to the stable version (`npm dist-tag add pkg@0.1.0 latest`);
- **canary / pre-release**: try a small scope first, then go fully live;
- **post-release monitoring**: watch logs/metrics; hotfix if a bug appears.

> **【do】Experience note**: actually going through one "crash and rollback" is worth more than reading "have a rollback plan" ten times.

---

## Checklist {#sec-5}

- [ ] Can **decide the version number correctly** based on the nature of the change.
- [ ] Can write a CHANGELOG containing **breaking changes + a migration guide**.
- [ ] Can state the **main stages** of the CI/CD pipeline.
- [ ] Can state the correct way to roll back when "npm cannot withdraw a published version" (deprecate + publish a fixed version + dist-tag back to stable), and the monitoring points.

**Follow-up** (look back at §6.1 if stuck): you removed a public tool and added a new replacement. Is that a breaking change? How should the version number and changelog be written?
