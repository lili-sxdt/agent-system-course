# Chapter 4: Lifecycle

> A plugin is not "mount and done." It has its own **life**: loaded → initialized → working → unmounted. This chapter lays that out, especially the part **beginners most often overlook: cleanup.**

---

## 4.1 When a plugin loads / initializes {#sec-1}

**In plain terms**: after a plugin is mounted into the container, the container **wakes it** at the right moment: "your turn, get to work."

**Technical**: typical lifecycle hooks:

| Stage | What it does | Analogy |
|---|---|---|
| load / apply | the plugin is registered, takes effect | reporting for duty |
| start / ready | establish connections, prepare resources | powering on the computer, going online |
| running | respond to events, handle requests | the normal workday |
| dispose | release resources, disconnect | resigning, handing over |

```ts
export function myPlugin(ctx: Context) {
  // on load: register capabilities
  ctx.tool(readFileTool)

  // on ready: do initialization
  ctx.on('ready', () => {
    console.log('my plugin is ready')
  })

  // on dispose: clean up (very important, see 4.3)
  ctx.on('dispose', () => {
    console.log('cleanup done')
  })
}
```

---

## 4.2 Ordering and dependencies {#sec-2}

**In plain terms**: some plugins are "can't work without it" — e.g., a "tool" depends on the "container" being ready first. **If the order is wrong, it gets called before it is ready, and it errors immediately.**

**Technical**: the container decides load order through **dependency declaration**: A declares it depends on B, so B loads first. This is **dependency topological sorting.**

```ts
// Illustrative: declare dependencies; the container guarantees the dependency is ready first
ctx.inject(['logger'], (ctx) => {
  ctx.logger.info('logger is ready, so I begin')
})
```

**Key**: **do not assume "when I load, others are already ready."** Use dependency declarations and let the container sort it for you.

---

## 4.3 Unmount and cleanup {#sec-3}

**In plain terms**: when a plugin "gets off work," it must **clean up the mess it made** — turn off timers, disconnect, unregister listeners. Not cleaning up **leaks resources**; over time the system slows down or even crashes.

**Technical**: the `dispose` stage must **release every held resource** to avoid memory leaks, handle leaks, and accumulating event listeners. **The "unmount" in "mountable and unmountable" means unmounting cleanly.**

```ts
export function myPlugin(ctx: Context) {
  const timer = setInterval(() => {/* ... */}, 1000)

  ctx.on('dispose', () => {
    clearInterval(timer)   // ← if not cleaned, this timer lives forever
  })
}
```

> **The most common beginner mistake**: write only "startup," not "cleanup." In the short term nothing looks wrong; in the long term it breaks.

## Checklist {#sec-4}

- [ ] Can state the **four lifecycle stages** (load / initialize / work / unmount).
- [ ] Can explain **why dependency declarations are needed** (order, avoid being called while not ready).
- [ ] Can give an example of a resource that **must be cleaned** (timer / connection / listener).
- [ ] Knows that "mountable and unmountable" "unmount" means **unmounting cleanly.**

**Follow-up** (look back at §4.3 if stuck): your plugin starts a `setInterval` timer but does not clean it up in `dispose`. If you "mount → unmount" it 100 times, what happens?
