# Chapter 2: Dependency Injection (DI) and the Container

> The previous chapter said "split into plugins." But once split, **who manages them, and who ties them together?** The answer is the **container.** This chapter clarifies: what dependency injection (DI) is, and what the container does.

---

## 2.1 What problem DI solves {#sec-1}

**In plain terms**: suppose A needs B. The most instinctive approach is for **A to `new B()` itself.** But then A is "welded" to B — to swap in a B' you must change A.

**Switch to DI**: A **does not build B itself; instead it tells the container "I need a B."** The container handles handing B to A. A only uses it, and does not care where it came from.

**Technical**: **dependency injection (DI)** is a design in which "dependencies are passed in from outside rather than created internally." It makes components **depend on interfaces rather than implementations**, enabling decoupling, replaceability, and testability. The underlying idea is **inversion of control (IoC)** — control shifts from inside the component to the container.

```ts
// hard-coded: A is welded to B
class A { private b = new B() }

// DI: A just says "I want a B," and the container gives it
class A { constructor(private b: B) {} }
```

---

## 2.2 The role of cordis / context {#sec-2}

**In plain terms**: DSH uses **Cordis** as the "container," and its core object is **context (ctx).** You put plugins into ctx, and plugins find and use each other through ctx.

**Technical**: Cordis is a **plugin container / IoC framework**. `ctx` is the context object running throughout the system, offering registration, dependency, event, and lifecycle capabilities. All `dsh-*` packages are "plugins registered into ctx" — that is how DSH is organized.

```ts
const app = new Context()
app.plugin(myPlugin)      // mount the plugin into the container
```

---

## 2.3 What is inside the container {#sec-3}

A container roughly manages three things:

| Thing | In plain terms | Purpose |
|---|---|---|
| **registry** | the roster | records "which plugins/services are in the system" |
| **services** | public facilities | capabilities a plugin provides that others can use |
| **lifecycle** | the power-on/off flow | controls when plugins load, initialize, and unmount |

**In one sentence**: **the container is a "steward" responsible for registering, distributing, and switching on/off.** Plugins just do the work; they do not worry about "how I am managed in the system."
