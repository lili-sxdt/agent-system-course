# Chapter 5: The Configuration System

> The final chapter. For a plugin to be "customizable on demand," it needs a **configuration system.** This chapter covers: how to define configuration items, how to rank their priority, and how to validate and write them back.

---

## 5.1 How to define a plugin's configuration {#sec-1}

**In plain terms**: give the plugin a "settings sheet" — what can be tuned, what the defaults are, what the types are. The user only changes the few items they care about.

**Technical**: use a **schema** to declare configuration: field names, types, defaults, validation rules. When the container loads the plugin, it merges user config with defaults and passes the result to the plugin.

```ts
export interface MyPluginConfig {
  /** whether the status bar is enabled */
  enabled: boolean
  /** polling interval (milliseconds) */
  pollMs: number
}

const defaultConfig: MyPluginConfig = {
  enabled: true,
  pollMs: 5000,
}
```

**Benefit**: type safety + defaults + validation. **Do not let a plugin discover "config is missing" only at runtime.**

---

## 5.2 Priority: default < user < preset {#sec-2}

**In plain terms**: configuration may come from several sources — who wins? In this order (later overrides earlier):

```
default  <  user config  <  preset / command line
```

**Technical**: configuration **merging** follows priority: the base is the default, user config overrides it, and a specific scenario (preset, command-line arguments) overrides again. This gives sensible defaults plus fine-grained control.

```ts
const finalConfig = { ...defaultConfig, ...userConfig, ...presetConfig }
```

**Key**: **the more "temporary / specific," the higher the priority.** The user's change is "this project's" config; a preset is "this run's" override.

---

## 5.3 Write-back and validation {#sec-3}

**In plain terms**: when the user changes a setting, it must be **saved** (written back to a config file) so it persists; a bad value must be **caught** (validation) so it does not start up with broken config.

**Technical**:
- **Validation**: before writing back, check types/ranges with the schema; on failure, report an error and keep the original value.
- **Write-back**: serialize to a config file (e.g., JSON); use **atomic writes** (write a temp file, then replace) to avoid corrupting the config if a crash occurs mid-write.
- **Newline**: mind the trailing newline on write-back, to avoid a false "content unchanged but shown as modified" diff (a real pitfall in real projects).

```ts
function writeConfig(path: string, cfg: MyPluginConfig) {
  // Illustrative: a real project should do atomic write + validation
  fs.writeFileSync(path, JSON.stringify(cfg, null, 2) + '\n')
}
```

## Checklist {#sec-4}

- [ ] Can state **what a config item should declare** (type / default / validation).
- [ ] Can rank the **priority** (default < user < preset).
- [ ] Can state the **two things to watch on write-back** (validation, atomic write).
- [ ] Knows why "config write-back" must be careful about newlines/format.

**Follow-up** (look back at §5.3 if stuck): the user typed `"abc"` (a string) for `pollMs`. **When** should your plugin notice the problem — validate before startup, or crash halfway through a run? Why?
