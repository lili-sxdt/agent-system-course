# Chapter 3: The Registration Mindset

> The previous two chapters covered "go plug-in and manage with a container." This chapter teaches you **how to talk to the container concretely**: by "registering" things into it. Master these few lines and you can add capabilities to the system.

**The core mindset in one sentence**: **do not go around `new`-ing things; instead "register with the container."**

---

## 3.1 `ctx.plugin()`: joining the system {#sec-1}

**In plain terms**: hand the plugin you wrote **to the container**, and it "joins the team."

```ts
ctx.plugin(myPlugin)          // mount a plugin
ctx.plugin(myPlugin, options) // mount a plugin with configuration
```

**Technical**: `ctx.plugin(fn, config?)` registers the plugin function into the container; the container calls it according to its lifecycle and passes the config in. **This is the first line of a plugin's relationship with the system.**

---

## 3.2 `ctx.tool()` / `ctx.skill()`: registering capabilities {#sec-2}

**In plain terms**: to give the agent a "thing it can do" (a tool) or "knowledge it can talk about" (a skill), you **register it with the container** rather than stuffing it into some big file.

```ts
ctx.tool(readFileTool)   // register a tool: the agent can now call it
ctx.skill(mySkill)       // register a skill: the agent can read it when needed
```

**Technical**: `ctx.tool()` / `ctx.skill()` are the entry points for "capability registration." After registration, the system **auto-collects** them into the "available tools / skills list" during assembly and hands them to the model. **You only register; collecting and distributing is the container's job.**

> This is why in DSH "writing a SKILL.md gets it loaded" — at heart it is **registration**.

---

## 3.3 `ctx.on()`: listening to events and hooks {#sec-3}

**In plain terms**: the system fires various "events" (loaded, user spoke, about to unload…). You can **attach a hook**: "when this happens, do a bit of my thing."

```ts
ctx.on('ready', () => console.log('system ready, my plugin starts working'))
ctx.on('dispose', () => console.log('system shutting down, I clean up here'))
```

**Technical**: `ctx.on(event, handler)` subscribes to an event. Event-driven design **decouples** plugins — A does not call B directly; A fires an event and B listens.

---

## 3.4 Convention over configuration {#sec-4}

**In plain terms**: do not make the user fill everything. **Whatever can have a sensible default, set it**; the user only changes what they actually care about.

**Technical**: **convention over configuration** — use reasonable defaults to reduce cost of use, and expose configuration only when necessary. Most DSH plugins "work by convention once mounted, and only need configuring when required."
