# Chapter 1: Why Go Plug-in

> From this part onward, we give the mini-harness a "skeleton." The first thing: **split capabilities into plug-in units.** This is the fundamental reason DSH can hold several hundred modules without falling apart.

The bare agent you built in Part 1 §5 crammed everything into one file. It runs, but **change one place and everything is affected.** This chapter covers how to split it apart.

---

## 1.1 Break capabilities into plug-in units {#sec-1}

### 1.1.1 One capability = one plugin

**In plain terms**: do not cram "read a file, compute, browse the web, log" all into one program. **Make each capability a "plugin"** — a self-contained little box with its own switch.

**Technical**: a **plugin** is a self-contained capability unit, loaded by the system according to a unified interface. The system does not need to know how a plugin is written internally; it only needs it to follow the convention of "how to mount, how to unmount, and what it provides."

### 1.1.2 How a plugin is "mounted / unmounted"

**In plain terms**: mount = add it to the system and let it start working; unmount = remove it, stop it, and clean up. **Being able to mount and unmount is what makes it a plugin.**

```ts
// Illustrative: a plugin is a unit the system can load
export function myPlugin(ctx: Context) {
  ctx.on('ready', () => console.log('plugin loaded'))
}
```

---

## 1.2 The advantages of plugins {#sec-2}

### 1.2.1 Reuse

Write a "read file" plugin once and any project can mount it. **No reinventing the wheel.**

### 1.2.2 Switching & control

Want it, mount it; don't want it, unmount it. **A broken plugin can be switched off with one click** without affecting other features — this is key to "operability."

### 1.2.3 Independent evolution

Plugins **do not interfere with each other**: changing plugin A does not break plugin B. Teams can develop in parallel (remember our discussion of "how to assign people"? This is what makes it possible).

---

## 1.3 Compare with a "hard-coded program" {#sec-3}

| | Hard-coded program (bare agent) | Plug-in |
|---|---|---|
| change one feature | touch the whole file, easy to break elsewhere | change only that plugin |
| add/remove a feature | edit code, redeploy | mount/unmount a plugin |
| multi-person collaboration | stepping on each other's toes | each writes their own plugin |
| reuse | copy-paste | just mount it |

**In one sentence**: **plug-in = turn "one big blob" into "a pile of building blocks."** This is the first step from "it runs" toward "it is maintainable and extensible."
