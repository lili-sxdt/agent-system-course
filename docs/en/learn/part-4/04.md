# Chapter 4: Security and Sandboxing (Sandbox / Permissions)

> This is the **most important chapter in Part 4**. The previous chapters let the agent "do more"; this one puts **reins** on it. **An agent without security boundaries is more dangerous the more capable it is.**

---

## 4.1 Risk awareness {#sec-1}

**In plain terms**: an agent that can read files, run commands, and make network requests — if **unattended** — what could it do? Delete your files, send out your keys, run a malicious script… **It is not malicious; it genuinely "has the ability."**

**Technical**: an agent's risk surface includes **file destruction, command injection, data exfiltration, privilege escalation, and burning money in infinite loops**. The core principle: **least privilege** (grant only the minimum capability needed to complete the task).

---

## 4.2 Sandbox models: local vs. isolated {#sec-2}

**In plain terms**: draw a "fence" around the agent. There are two kinds:

| Model | Description | Cost |
|---|---|---|
| **local sandbox** | on your machine, but with restricted directories/commands | light, but isolation is not thorough |
| **isolated sandbox** | a separate process / container / VM | heavy, but safer |

**Technical**: a local sandbox relies on **path restrictions + command allowlists + resource limits**; an isolated sandbox uses **containers/VMs/separate users** for process-level isolation. **The higher the risk, the more you should isolate.**

**Key**: DSH does this in layers — path restrictions, a command sandbox, permission tiers, and approvals. **Security is "defense in depth," not "one wall."**

---

## 4.3 Permission tiers: read-only / write-workspace / full access {#sec-3}

**In plain terms**: you do not need "maximum privilege" every time. Grant as needed:

| Level | What it can do | Suited to |
|---|---|---|
| **read-only** | look, not change | research, analysis |
| **write-workspace** | read/write within the workspace | most development tasks |
| **full access** | anywhere on the system | rare, requires explicit authorization |

**Technical**: **permission tiers** keep "risk controlled as capability grows." Default to the **lowest sufficient** level, and **explicitly escalate** when higher is needed (often requiring user confirmation).

---

## 4.4 Why this is the lifeline of such systems {#sec-4}

**In plain terms**: the more capable the agent, the bigger the consequence of a mistake. **Functionality and security are two sides of the same coin.**

**Technical**: the **trust model** of an agent system determines whether it can be truly used in production. Without a sandbox and permissions, an agent can only be "toy-grade"; with them, you dare let it touch real data and real systems. **This is also why DSH makes `dsh-sandbox-*`, `dsh-fs-*`, and `dsh-user-approval` into separate plugins.**
