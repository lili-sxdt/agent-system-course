# Chapter 5: Approval and Authorization

> A sandbox and permissions are "the system blocks automatically." But some operations **must be decided by a human** — that is **approval.** It is the last and most flexible line of defense.

---

## 5.1 Let the user confirm key operations {#sec-1}

**In plain terms**: when facing an operation that "could go wrong," the agent should not decide on its own; it should **stop and ask**: "I'm about to delete this file, are you sure?"

**Technical**: **approval** is the mechanism that pauses the flow and requests user confirmation before a sensitive operation executes. Execute after confirmation; abort and inform the model on refusal.

```
model wants to delete a file → hits an "needs approval" rule → pause → ask the user → delete if approved / inform the model if refused
```

**Key**: approval must be **well-informed** — state clearly "what it will do and what it affects," so the user can judge.

---

## 5.2 Sensitive-operation list and release rules {#sec-2}

**In plain terms**: you cannot ask about everything (annoying), nor about nothing (risky). Keep a **sensitive-operation list** and ask only when it matches.

**Technical**: typical operations needing approval:

| Category | Examples |
|---|---|
| **destructive file operations** | delete, overwrite, batch move |
| **running arbitrary commands** | shell commands, scripts |
| **outbound network** | uploading files, requests carrying sensitive data |
| **out-of-bounds access** | paths outside the workspace |
| **spending a lot** | large token usage, batch tasks |

**Release rules** can be tiered:
- **always allow** (reading workspace files);
- **always ask** (delete, run commands);
- **never automatic** (accessing keys, system directories).

---

## 5.3 Auditable traceability {#sec-3}

**In plain terms**: when something goes wrong, you must be able to check — **who, when, and what the agent was told to do.**

**Technical**: an **audit log** records each sensitive operation: time, operation type, arguments, approver, and result. It serves both security traceability and "post-mortem improvement."

```jsonl
{"ts":"2026-09-08T16:13","op":"delete_file","arg":"old.csv","approved":true}
```

**Key**: the audit log **must not contain keys**; it must be **tamper-resistant** (at least append-only, never overwrite).

---

## Checklist {#sec-4}

- [ ] Can state the **purpose of approval** (pause before a sensitive operation, request confirmation).
- [ ] Can list **at least four categories** of operations needing approval.
- [ ] Can state the **tiers of release rules** (always allow / always ask / never automatic).
- [ ] Can state what the audit log should record, and that it "must not contain keys."

**Follow-up** (look back at §5.2 if stuck): if every operation popped up a dialog asking the user, what problems would arise? How do you balance "safe" and "annoying"?
