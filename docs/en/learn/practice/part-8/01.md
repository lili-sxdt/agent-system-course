# Example 1 · Growing the System: Layered Architecture

> Goal: a small system's "it runs" does not mean "it scales." **Separating responsibilities** is what lets you add features without adding chaos.

<!-- 双向导航: 回主线 -->
> 📚 **Build on the main line first**: this exercise corresponds to **[Main Line, Part 8](/en/learn/part-8/01)** — read the main-line concepts first, then do the exercise.

## L1 Start with a "division of labor" {#sec-1}

Break the Agent into a few layers, each minding its own business:

```
┌─────────────────────────────┐
│ 应用层   （谁在用：CLI / Web）│
├─────────────────────────────┤
│ 编排层   （跑循环、调度工具）│
├─────────────────────────────┤
│ 能力层   （工具 / 技能 / 插件）│
├─────────────────────────────┤
│ 模型层   （API 调用、流式）  │
└─────────────────────────────┘
```

> **Mind one layer at a time**: to add a tool, touch only the capability layer, not the orchestration layer.

## L2 Dependencies point "inward" {#sec-2}

**Upper layers depend on lower layers; lower layers never depend on upper layers** — this is the iron rule of layering.

```ts
import fs from 'node:fs/promises'

// ✗ 坏：工具层回传界面消息（反向依赖）
// ✓ 好：工具只返回数据，界面由应用层拼
tool: async (_ctx: any, path: string) => ({ data: await fs.readFile(path, 'utf8') })
```

> (Illustrative example; `fs`/`path` are only for illustration. The point is: **the tool layer only returns data, it doesn't assemble the UI.**)

> **Why**: once a lower layer knows "who is on top of it," it can never be split apart or swapped again.

## L3 Module Size: Independently Replaceable {#sec-3}

**One module, one responsibility, one entry point** — to swap an implementation, you only touch one place.

```ts
// 模型层 —— 只暴露一个接口
export interface LLM {
  chat(messages: Msg[], opts?: ChatOpts): Promise<Reply>
}
// 想换模型？换一个实现这个接口的东西就行
```

> **Check**: can you replace a module without touching anything else? Yes → responsibilities are clear. No → the coupling is too deep.

## Variant Exercises (Apply It) {#sec-4}

1. **Extract tool registration into its own module**, and let the orchestration layer call only its entry point.
2. **Swap in a mock implementation of the model layer** and verify the app layer doesn't have to change.

## General Pattern: Layering Means "One-Way Dependencies + Single Responsibility" {#sec-5}

**Layering isn't for looks** — it's so that "changing one place doesn't affect anywhere else." Two iron rules: **dependencies run one way** (upper → lower) and **modules have a single responsibility** (one module does one thing). Independently replaceable = good architecture.
