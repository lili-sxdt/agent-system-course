# Example 2 · Integration: Making the Parts Match Up

> Goal: each part is fine on its own, but **they break when put together** — integration is about "in a real environment, lining up the interfaces one by one."

<!-- 双向导航: 回主线 -->
> 📚 **Build on the main line first**: this exercise corresponds to **[Main Line, Part 8](/en/learn/part-8/01)** — read the main-line concepts first, then do the exercise.

## L1 Aligning Interfaces: Define the "Contract" First {#sec-1}

The biggest pitfall in integration is "each side assumes the other looks like X." First define the **contract** (a shared agreement), so nobody has to guess.

```ts
// contract.ts —— 双方共同依赖的唯一事实源
export interface ToolCall {
  name: string        // 工具名（必须一致）
  args: Record<string, unknown>
}
export interface ToolResult {
  content: string     // 返回给模型的文本
  isError?: boolean
}
```

> **Put the contract in a shared file**, not a copy on each side — two copies will eventually diverge.

## L2 Run Through a Real Scenario {#sec-2}

Unit tests are "ideal inputs"; integration is "real messy inputs." Focus on the **edge cases**:

```ts
// 空输入、超长、特殊字符、缺字段
const cases = [ { args: {} }, { args: { path: '' } }, { args: 42 } ]
for (const c of cases) {
  const r = await route('tool.read', c)   // 看它会不会崩、会不会误报
  console.log(r)                          // 应当优雅失败，不抛异常
}
```

> **Any node that "reads the outside world"** (files, network, API) must test "what do you do when it hands you something weird."

## L3 End-to-End Handshake: One Complete Run {#sec-3}

```
请求 ──►【编排】──►【工具】──►【模型】──►【输出】
                ▲                  │
                └── 工具结果回填 ──┘
```

Run one **real task** and watch four seams: **①did the request come in; ②was the tool called; ③was the result fed back; ④did it output to the model.** Whichever seam breaks, that's where the problem is.

## Variant Exercises (Apply It) {#sec-4}

1. **Define a tool contract** shared by the "tool registration side" and the "caller side."
2. **Add "weird input" guards to tools**: missing fields and type errors all return gracefully.
3. **Run a real task** and point out which seam is most likely to break.

## General Pattern: Contract First + Real Inputs + Watch the Seams {#sec-5}

**Integration in three steps**: ①**contract first** (shared types, one authoritative copy); ②**real/weird inputs** (ideal inputs won't expose problems); ③**watch the seams** (request → tool → feed back → output, four points, locate the break). **Wherever you read the outside world, that's where you focus integration.**
