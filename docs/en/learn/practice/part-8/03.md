# Example 3 · Acceptance: The Check Before Delivery

> Goal: before release, **go through a checklist item by item** to confirm "either it really works, or you clearly know where it doesn't" — not "it seems fine."

<!-- 双向导航: 回主线 -->
> 📚 **Build on the main line first**: this exercise corresponds to **[Main Line, Part 8](/en/learn/part-8/01)** — read the main-line concepts first, then do the exercise.

## L1 Acceptance Checklist: Check Off Item by Item {#sec-1}

Go through a checklist before delivery rather than trusting a feeling of "it should be fine."

```
□ 核心任务能跑通（例：读文件→分析→回答）
□ 失败场景优雅处理（模型挂了、文件不存在）
□ 无越权行为（不乱写文件、不滥调工具）
□ 日志能定位问题
□ 简单任务不报错、速度可接受
□ 有一份「怎么用」的说明
```

> **A checklist must be "checkable"**: each item lets you clearly judge "pass / fail," with no ambiguity.

## L2 Acceptance Criteria: Write Down Clearly "What Counts as Working" {#sec-2}

**Acceptance criteria = quantifiable and reproducible**, not "the effect is a bit better."

| Item | Criterion (measurable) |
|---|---|
| Correctness | All 10 fixed tasks complete |
| Stability | Runs 50 times in a row without crashing |
| Cost | Single-task token consumption < threshold |
| Latency | Single task < 30s |
| Safety | All unauthorized access is rejected |

> **Translate "good" into numbers**: only then does acceptance have a basis, and only then will users trust you. "Very smooth" cannot be accepted; "<30s and 50 runs without crashing" can.

## L3 Adversarial Acceptance: Deliberately Find Faults {#sec-3}

Be your own **picky user**, deliberately trying the scenarios "most likely to succeed when they shouldn't":

```
1. 让它读不存在的文件 —— 应优雅报错，不崩
2. 让它越权删文件 —— 应拒绝
3. 用极强的恶意输入 —— 应不照做
4. 并发跑多个任务 —— 应不互相干扰
```

> **Acceptance isn't about proving "it works"; it's about forcing yourself to "find where it will break."** If you can't find anything → only then you dare to ship it.

## Variant Exercises (Apply It) {#sec-4}

1. **Write an acceptance checklist for your project**, as checkable as possible.
2. **Translate "smooth" into 3 measurable criteria.**
3. **Do one run of "deliberate fault-finding"**: list 3 scenarios where it might break.

## General Pattern: Checklist + Quantified Criteria + Deliberate Fault-Finding {#sec-5}

**The acceptance trio**: ①**checklist** (item-by-item, checkable); ②**quantified criteria** (translate "good" into numbers); ③**deliberate fault-finding** (deliberately step on the most dangerous scenarios). **Passing acceptance ≠ perfection, but "known boundaries, controlled risk."**
