# Example 3 · After Release: Feedback and Audit

> Goal: releasing isn't the end. **Collect feedback + independent audit** — only then do you know "where users struggle and where the pitfalls are."

<!-- 双向导航: 回主线 -->
> 📚 **Start with the main line first**: this exercise corresponds to **[Main Line Part 9](/en/learn/part-9/01)** — read the main-line concepts first, then get hands-on.

## L1 Collect Feedback: Are Users Actually Using It? {#sec-1}

The places users find uncomfortable are often the ones you didn't think of. **Collect proactively — don't wait for users to complain.**

```
反馈三渠道：
□ 日志：哪种任务失败最多？（数据说话）
□ 用户：哪个步骤觉得卡/不想要？（体验说话）
□ 社区：群里被问最多的问题？（说明哪没讲清）
```

> **Categorize the feedback**: is it "uncomfortable to use" (experience), "can't use" (bug), or "not explained clearly" (docs)? Different categories need different fixes.

## L2 Feedback Loop: Back to the Right Stage {#sec-2}

Feedback **needs somewhere to go** — not "received and done". You need to judge which step it should go back to for a fix.

```text
反馈「读文件老是失败」
  → 排查：是工具错（L2 能力层）？还是提示词没让用对（L1 编排）？
  → 定位到能力层 → 修工具 → 再发小版本
```

> **Key point**: don't just "patch it" — ask "was the design of this step right in the first place?". Feedback is **the entry point for improvement**, not a complaint.

## L3 Independent Audit: Don't Audit Yourself {#sec-3}

For important changes, get **another perspective** to find the issues — it's easy to "not see your own mistakes."

```text
自审：改完说「我觉得没问题」 —— 容易自我确认(有盲区)
独立审计：别人看你的改动，问「这里会不会崩」——更客观

→ 大版本 / 安全相关改动，一定要独立审计
```

> **Why independent**: after staring at this code for a long time you form a "fixed mindset" and can't see the hidden risks. A different perspective = an extra layer of protection.

## Variant Exercises (apply it) {#sec-4}

1. **Design a feedback collection form**: what information do you want to collect?
2. **Close the loop on one feedback to the right stage**: at which layer should it be fixed?
3. **Run one independent audit on an important change**: ask someone else / look from a different angle.

## General pattern: collect feedback + close the loop + independent audit {#sec-5}

**After release is a "growth cycle"**: **collect feedback** (logs / users / community) → **close the loop** (locate and fix at the right stage) → **independent audit** (a different perspective to avoid blind spots). **Self-indulgent releases have no vitality** — know how to "let users speak", and the system keeps getting better.
